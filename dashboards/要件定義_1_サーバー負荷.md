# サーバー負荷ダッシュボード 要件定義

作成日：2026-10-08　状態：実装済み

> **2026-10-09 変更（2）**：置き場所を `server_info/` から `dashboards/` に改名し、コードを `dashboards/programs/` に移した。画面は `dashboards/server.html`（もとの `dashboard.html`）。以下の本文のパスは、もとのままである。
>
> **2026-10-09 変更**：15 分ごとの定期更新（cron）をやめ、画面の「更新」ボタンを押したときに収集する方式にした（ユーザーの指示）。cron は登録していない。以下の本文のうち、「15 分ごと」「cron」「開き直すと最新」「更新が止まっています」の記述は、8 節の内容に置き換わる。

## 1. 目的

実験を流す前に「いまサーバーが空いているか」「いつ空きそうか」を、1 枚の画面で判断できるようにする。

## 2. 決定済みの前提

| 項目 | 決定内容 |
|---|---|
| 対象サーバー | BariKata の 1 台のみ（16 コア／メモリ 31GB／RTX 3090 24GB × 1） |
| 表示形式 | 静的 HTML。`server_info/dashboard.html` を作り直す方式 |
| 更新間隔 | 15 分に 1 回 |
| 表示項目 | CPU・メモリ、GPU、ディスク |
| 履歴 | 現在値に加えて、直近の推移も表示する |
| 対象外 | ユーザー別の CPU・メモリ占有、ログイン中ユーザーの一覧、通知（メール・Slack 等） |

## 3. 機能要件

### 3.1 収集（15 分ごと）

| 区分 | 項目 | 取得元 |
|---|---|---|
| CPU | 使用率（数秒間の平均）、ロードアベレージ 1 分／5 分／15 分、コア数 | `/proc/stat`、`/proc/loadavg` |
| メモリ | 総量、使用量、利用可能量（available）、スワップ使用量 | `/proc/meminfo` |
| GPU | 使用率、VRAM 使用量／総量、温度 | `nvidia-smi` |
| GPU プロセス | PID、実行ユーザー、VRAM 使用量、コマンド名 | `nvidia-smi` |
| ディスク | 総量、使用量、空き、使用率（`/` と `/mnt/hdd0`） | `df` 相当 |

- 15 分に 1 回の瞬間値だけでは、たまたまの谷や山を拾う。そのため CPU は「15 分ロードアベレージ ÷ コア数」を主指標にし、瞬間の使用率は補助として並べる。
- メモリは「使用量」ではなく「利用可能量」で空きを判断する（キャッシュ分を使用中と誤読しないため）。
- 一部の取得に失敗しても（例：`nvidia-smi` がエラー）、他の項目は記録し、失敗した項目は欠損として残す。

### 3.2 履歴の保存

- 収集のたびに 1 行を追記する（CSV）。置き場所は `server_info/history/`。
- 列にサーバー名を持たせ、将来サーバーが増えても同じ形式で溜められるようにする。
- 保持期間を過ぎた行は、収集時に削除する（期間は未決事項 2）。

### 3.3 ダッシュボード（`server_info/dashboard.html`）

上から順に、次の 3 つを置く。

1. **ヘッダー**：サーバー名、最終更新時刻。最終更新から 30 分以上たっていたら「更新が止まっています」と目立つ警告を出す（収集が止まったまま古い値を見続けるのを防ぐ）。
2. **現在値の一覧**：サーバー 1 台を 1 行とした表。列は CPU（15 分ロード÷コア数、使用率）、メモリ（利用可能量／総量）、GPU（使用率、VRAM、温度）、ディスク（マウントごとの使用率と空き）。各セルは、しきい値に応じて「余裕／混雑／逼迫」を色と文字の両方で示す。GPU を使っているプロセスがあれば、その下にユーザー・VRAM・コマンド名を並べる。
3. **推移グラフ**：CPU、メモリ、GPU 使用率、VRAM の折れ線。表示期間は直近 24 時間と直近 7 日を切り替える。ディスクは変化が遅いため、直近 7 日のみ。

- 外部の CDN やフォントを読み込まない、1 ファイルで完結した HTML にする（VSCode のプレビューでも、ダウンロードして開いても表示できるように）。
- 自動リロードはしない。開き直すと最新になる。

### 3.4 サーバーの追加に備える

- 対象サーバーは `server_info/servers.json` に書く。今は BariKata（ローカル取得）の 1 件。
- 一覧表・履歴・グラフは最初から複数台を前提にした形にしておき、将来 SSH 経由の取得を足すときに、画面と保存形式を作り直さずに済むようにする。SSH 取得そのものは今回は作らない。

## 4. 非機能要件

- **依存**：Python 3.10 の標準ライブラリと `nvidia-smi` のみ。追加インストールなし。
- **負荷**：1 回の収集と HTML 生成を 10 秒以内に終える。監視そのものがサーバーを重くしない。
- **権限**：一般ユーザー（yayoten）で動く。sudo 不要。
- **定期実行**：cron（`*/15 * * * *`）。現在 yayoten の crontab は空。
- **壊れにくさ**：HTML は一時ファイルに書いてから置き換える（生成途中の画面を見せない）。実行ログを `server_info/logs/` に残し、失敗の原因を追えるようにする。
- **研究用 DB との分離**：実験結果の `DB/` には書き込まない。

## 5. ファイル構成（案）

```
server_info/
├── 要件定義.md        この文書
├── README.md          使い方、cron の登録・解除方法
├── servers.json       対象サーバーの一覧
├── collect.py         収集して履歴に追記
├── build_dashboard.py 履歴から dashboard.html を生成
├── run.sh             cron から呼ぶ（collect → build）
├── dashboard.html     生成物
├── history/           生成物（履歴 CSV）
└── logs/              生成物（実行ログ）
```

## 6. 確認して決めたこと（提案どおり）

| # | 内容 | 提案 |
|---|---|---|
| 1 | 生成物（`dashboard.html`、`history/`、`logs/`）を git で管理するか | 管理しない（`.gitignore` に追加）。15 分ごとに差分が出続けるため |
| 2 | 履歴の保持期間 | 90 日。1 日 96 行なので、容量は問題にならない |
| 3 | 色分けのしきい値 | CPU（15 分ロード÷コア数）：0.7 以上で混雑、1.0 以上で逼迫／メモリ利用可能量：20% 未満で混雑、10% 未満で逼迫／VRAM 使用率：50% 以上で混雑、90% 以上で逼迫／ディスク使用率：80% 以上で混雑、90% 以上で逼迫 |
| 4 | cron の登録を誰がするか | 実装後に登録コマンドを提示し、確認を得てから Claude が登録する |
| 5 | 時刻の表示 | 日本時間（JST） |

## 7. 完成の判定

- `run.sh` を手で 1 回実行すると、履歴に 1 行増え、`dashboard.html` の最終更新時刻が変わる。
- cron 登録後、1 時間で履歴が 4 行増える。
- `nvidia-smi` が失敗する状況でも、CPU・メモリ・ディスクは記録され、画面は表示される。
- 履歴が 1 行しかない状態、0 行の状態でも、画面が崩れない。
- 収集を止めて 30 分たつと、画面に更新停止の警告が出る。

## 8. 2026-10-09 の変更（ボタンで更新）

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 更新のきっかけ | cron で 15 分ごと | 画面の「更新」ボタン。定期更新はしない |
| 表示形式 | 静的 HTML を直接開く | `serve.py`（標準ライブラリの HTTP サーバー、既定は 127.0.0.1:8765）が `dashboard.html` を配る。ボタンが `POST /refresh` を送り、`run.sh` を動かしてから再読み込みする |
| 古い値の警告 | 「更新が止まっています」 | 「最後の更新から○分たっています。『更新』を押すと最新になります」（30 分以上） |
| 履歴・推移グラフ | 15 分おきの等間隔 | ボタンを押した時刻だけ。間が `line_gap_minutes`（60 分）より空いた区間は線をつながない |
| 設定 | `interval_minutes` | 廃止。代わりに `line_gap_minutes` |

- 静的 HTML だけでは、ボタンからサーバー上の収集を起動できないため、配信用のプログラムを足した。追加のインストールは不要。
- 完成の判定の「cron 登録後、1 時間で履歴が 4 行増える」は、「『更新』を 1 回押すと、履歴が 1 行増え、最終更新時刻が変わる」に置き換える。
