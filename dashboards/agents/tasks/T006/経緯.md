## 1. 一言で（このタスクは、何のために、なぜ今あるのか）

これまでの実験（W001 の旧 REP001・002 など）は、記録した量が足りず、あとから「この量も要る」と分かって、**実験を流し直す羽目**になっている。今後、同じことが起きないよう、実験のたびに「考えられる限り細かい情報」を記録し、溜まったデータを再解析するだけで新しい問いに答えられるようにする。そのための記録の追加と、DB の再設計が、このタスクである。

## 3. 流れ（時系列）

1. 2026-10-10、Q001 の REP006（超過を買い方 E・見積もりの偏り P・抽選 L に分ける）を設計していて、E・P・L を作るには、$N_\mathrm{est}$（落札して露出した機会の推定価値の和）と $N_\mathrm{real}$（雑音を加えたあとの確率の和）が要ると分かった。**今の DB の `ticks` 表には、どちらも無い**（あるのは `pvalue_mean`：全機会の平均、`n_exposed` など。落札した機会は推定価値が高いほうに偏るので、`pvalue_mean` では代用できない）。`tick_hook` が渡す情報にも、雑音を加えたあとの確率が無い。
2. そのため、W001 の再実施（T003：ルールベース 3 手法、完了。T004：学習ベース 5 手法、評価 720 run のうち 661 run で、ユーザーの指示により 2026-10-10 に中止）の run も、REP006 のためには流し直しが要る。ユーザーは、この種のやり直しが続くことを避けたいと述べた。
3. `DB/runs/` には今、約 1,400 run が入っている（137MB）。保存しているのは、`episodes`・`ticks`・`agents` の集計だけで、入札額・機会ごとの値・時間の細かい内訳・手法の内部状態は無い。
4. リポジトリの今の使用量は約 106GB（2026-10-10、`du`）。内訳は `DB/dataset/` 93GB（公開の学習データ。消さない）、`.git` 6.3GB、`DB/models/` 4.2GB、`.venv` 2.2GB、`DB/runs/` 137MB。200GB の上限までの余裕は、**約 94GB**。
5. 2026-10-10、W001 の REP の番号を付け替えた（もと REP003 → REP001、REP001 → REP002、REP002 → REP003。対応表：`research/W001_既存手法の比較/REP番号の対応表.md`）。DB の `rep` の値（`REP001` など）は、もとのまま。

**Claude の見積もり（確かめていない。担当が実測で置き換える）**

- 1 run は、4 エピソード × 約 50 万機会。プレイヤー 1 社だけの機会ごとの記録（1 行 8 列、float32）で、1 run 約 64MB（圧縮前）。864 run で約 55GB。
- 48 社全員の機会ごとの記録は、その約 48 倍になり、容量に収まらない。**全員ぶんは、ティックごとの集計**で持つのが現実的と考えた。
