# T006 実験記録の全面拡充（DB の再設計）

> 無人で動く Claude への指示書。起動した Claude は、まず `経緯.md`（このタスクができるまでの流れ）、次にこの文書と `.claude/rules/unattended.md` を読む。
> 進み具合は、下のチェックリストに印を付け（`- [x]`）、`進捗.md` に書く。画面の「進み具合」は、この印の数で出る。

## 目的

実験をやり直しにしないため、**考えられる限り細かい情報**（時間・メモリ・ティックごとの全員の集計・機会ごとの値・雑音・手法の内部状態など）を、実験のたびに記録できるようにし、DB を再設計する。**何が取れるかの検討も、担当（あなた）が行う**（ユーザーは席を外していて、決められない）。

## 進め方の決まり（このタスク固有）

1. 最初に、`経緯.md`、この文書、`.claude/rules/unattended.md`、`CLAUDE.md`、`research/README.md`（8.）、`DB/README.md`、`github/Test/README.md`・`github/Test/1_初期セットアップ/README.md`・`github/Test/2_学習データと学習手法/README.md`、Q001 の `REP006_…/REP006.md`（2.2.2 と 8.1 節。E・P・L に要る量）を読む。`python3 dashboards/programs/agentctl.py list` と `git status` で、他のタスクと、他の Claude の未コミットの変更を確かめる。
2. **何を取るかは、「あとから聞かれうる問い」から考える。** 取れる量を洗い出すときは、次の観点を、すべて検討する。取らないと決めた量は、理由を `DB/記録の一覧.md` に書く。

   | 観点 | 例（候補。これに限らない） |
   |---|---|
   | 時間 | 1 run・エピソード・ティックの実行時間（壁時計、CPU 時間）、各手法の `bidding()` 1 回の時間、シミュレータの各段（順位づけ、支払い、露出、雑音、抽選、予算超過のやり直し）の時間、`adjust_over_cost` のやり直しの回数 |
   | 資源 | メモリ（最大、ティックごと）、並列数、端末、CPU 数、ライブラリの版、起動時刻・終了時刻 |
   | 再現 | 乱数のシード（環境・露出・雑音・抽選・手法・学習）、コミット、`github/` の版、設定の全文、重みの SHA-1 |
   | ティック × 全 48 社の集計 | 入札額の分布（平均・分位点）、α（実効入札係数）、落札数・枠別、支払い、残り予算、購入数、予算切れの時刻 |
   | プレイヤーの機会ごとの値 | 推定価値、σ、雑音を加えたあとの確率、入札額、枠、支払い単価（次点の入札額）、露出、抽選の結果（可能なら、抽選に使った乱数の値）、打ち切りの幅 u1・u2、予算超過で取り消された入札 |
   | 手法の内部状態 | PID の内部変数、ABid・Online LP の表の参照結果、学習ベースの入力状態（16 次元）と出力 α、（取れるなら）Q 値 |
   | 環境の性質 | 広告主ごとの雑音の幅、各機会の競合の入札額の上位、市場価格の分布 |
   | 派生量（REP006 用） | $N_\mathrm{est}$、$N_\mathrm{real}$、$\sum p(1-p)$（露出した機会の和）。**この 3 量は、必ず取る**（REP006.md 8.1 節） |

3. **記録を足しても、結果（購入・支払い・成績）を変えない。** 乱数の流れを変えない（記録のために乱数を引かない。乱数を作り直す関数を、追加で呼ばない）。変えていないことは、**既存の run と全セルで一致すること**で確かめる（たとえば、`research/W001_既存手法の比較/再実施_ルールベース/params/check_same_as_old.json` の 18 run と同じ設定を、新しいコードで流し、`reward`・`all_cost`・`score_component` が全セルで一致すること）。
4. **容量の制約：リポジトリ全体で 200GB まで。** 今は約 106GB（`DB/dataset/` 93GB は消さない）。余裕は約 94GB。
   - 記録は、**段**に分けて設計する（たとえば、全 run で取る「標準」と、一部の run だけで取る「詳細」）。段ごとに、1 run のサイズを、**1 位置のパイロット（4 エピソード）で実測**し、864 run（ルールベース 144 + 学習ベース 720）で何 GB になるかを見積もる。
   - 見積もりが、余裕の 6 割（約 56GB）を超える段は、「標準」にしない。超える段は、ユーザーが選べるように、`進捗.md` に書く。
   - 容量は、`du -sh` で測り、実測と見積もりを `DB/記録の一覧.md` に書く。圧縮（parquet の zstd など）、型の縮小（float32 など）、行の絞り込み（落札・露出した機会だけ）を使ってよい。
5. **DB の設計は、担当に任せる。** 既存の run（`DB/runs/` の約 1,400 run、`ticks`・`episodes`・`agents`）と互換にし、既存の列は残す（`research/` の既存の解析スクリプトが動くこと）。新しい表・列は、`DB/make_columns.py` に、意味・単位・「なぜ取るか」を書く。`DB/build_db.py` で、新旧の run をまとめて索引にできるようにする。
6. **`github/` を変えるので、`CLAUDE.md` の決まりに従う。** `github/Test/1_初期セットアップ/` の pytest を**全件**回し、変更点には回帰テストを足す。新しいテストは、`github/Test/3_実験記録の拡充/`（新設。`README.md` を作る）に置く。`github/Test/README.md` に、この新しいフォルダの行を足す（このファイルには、他の Claude の未コミットの変更がある。**足した行だけを自分の変更とし、そのファイルはコミットしない**。`進捗.md` に「README への追記が未コミット」と書く）。
7. 流し直し（REP002・REP003 のやり直し、再実施）は、**このタスクではやらない**。パイロット（1 位置）と、テストに要る範囲だけ流す。重い処理を流す前に、`free -g` と `uptime` で空きを確かめ、**並列は 4 まで**（1 本 約 2.9GB）。
8. **コミット。** 区切りごとに、自分が変えたファイルを名前で指定し、種類で分けて（`github/` の変更＋テスト／DB の設計／記録の一覧・報告）コミットする。`git -c user.name=yayoten -c user.email=g2222077@tcu.ac.jp commit …`（このサーバーの tmux では、git の作者が未設定のため）。**push はしない**（ユーザーの承認が要る）。終わるとき、`進捗.md` に「push 待ち」とコミット一覧を書く。
9. 他の Claude・ユーザーの未コミットの変更（`CLAUDE.md`、`.claude/`、`dashboards/`、`research/MASTER.md`、`research/Q001_…/` 配下など）に触らない。巻き込んでコミットしない。
