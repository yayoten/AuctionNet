# T010 実行の高速化（結果を変えずに、メモリと時間を減らす）

> 無人で動く Claude への指示書。起動した Claude は、まず `経緯.md`（このタスクができるまでの流れ）、次にこの文書と `.claude/rules/unattended.md` を読む。
> 進み具合は、下のチェックリストに印を付け（`- [x]`）、`進捗.md` に書く。画面の「進み具合」は、この印の数で出る。

## 目的

評価の 1 run（約 90 秒・約 3GB）の**時間とメモリを、結果を変えずに減らし**、並列を増やして、864 run の流し直し（T007）を速くする。あわせて、**負荷（メモリ・CPU とも約 90%）の上限の中で、並列数を自動で決めて流す**仕組みを作る。

## 進め方の決まり（このタスク固有）

1. **前提：T009（DB の作り直し）が完了していること。** 最初に `agentctl.py list` で確かめる。完了していなければ、`進捗.md` に書いて止める。
2. 最初に、`経緯.md`、この文書、`.claude/rules/unattended.md`、`CLAUDE.md`、`research/README.md`（8.）、`DB/README.md`（T009 で作り直された新しい構造）、`github/Test/README.md` と `1_初期セットアップ/`・`3_実験記録の拡充/`・`5_DBの作り直し/` の README、`github/simul_bidding_env/`（`Environment/BiddingEnv.py`、`PvGenerator`、`Controller`）、`github/run/run_test.py`、`research/src/run_experiment.py` を読む。`agentctl.py list` と `git status` で、他のタスクと他の Claude の未コミットの変更を確かめる。
3. **結果を変えない。これが最優先の決まりである。** 速くするための変更は、**以前の結果と、全セルで一致する**（`reward`・`all_cost`・`score_component`、`ticks` の値）ことを確かめてから採用する。**1 セルでも違えば、その変更は採用しない**（理由を `進捗.md` に書く）。比べる相手は、T009 が `DB/_legacy/` に退避した T006 の版 2 の run（ルールベース 3 手法 × 6 位置 × 4 エピソード、18 run）と、学習ベースの run（`DB/models/` の重みを使う。以前の run が `DB/_legacy/` にある。無ければ、変更前のコードで流して基準を作る）。**学習ベース（ニューラルネットの推論）を含む、少なくとも 5 手法 × 数位置で、一致を確かめる。**
4. **GPU は使わない**（経緯 4）。`torch` の入れ替え、依存のロックの変更も、しない。
5. **何から速くするか（担当が、実測で順位を決める）。** まず、時間とメモリの内訳を測る（`DB/` の新しい構造に入る、T006 の時間の記録が使える）。候補（経緯 3 の見積もり。確かめていない）：

   | 候補 | 内容 | 結果が変わらない理由 |
   |---|---|---|
   | 乱数の使い回し | 雑音（`_generate_values_matrix`）、抽選（`_calculate_conversion_action`）、露出（`_calculate_exposure`）の乱数を、エピソードごとに 1 回だけ作り、ファイル（`np.save`、mmap）で共有する | 入札に依らず、固定の種だけで決まる。作った配列を使い回すので、値は同じ |
   | 読み取り専用の大きい配列の共有 | PV のデータなどを、プロセス間で mmap で共有する | 値は同じ。メモリだけが減る |
   | 順位づけ（sort）・支払いの計算 | `np.argsort` を `np.argpartition` にする、など | **同順位の扱いが変わると結果が変わる**。同じ結果になることを、確かめてから |
   | 記録（T006 の追加分） | `hook` の処理を軽くする | 記録の値は同じ |
   | 背景の 47 社の `bidding()` | 手法の中の無駄な計算を省く | **結果が変わらないものだけ** |

6. **作ってよい仕組み：負荷を見て並列数を決めて流すランナー**（`research/src/run_parallel.py` など。名前は担当が決める）。メモリの使用（available）と CPU 使用率を監視し、**どちらも約 90% を超えない範囲**で、run を投入する。スワップを使い始めたら、投入を止める。1 プロセスのメモリは、実測で決める。**他の人が使っているサーバー（共用）なので、`/home/yayoten` の外のプロセスを止めない**。テストは、数 run で行う。
7. **コードの変更と版。** `github/` を変えるので、`CLAUDE.md` の決まりに従う：`github/Test/1_初期セットアップ/` の pytest を**全件**回し、変更点には回帰テストを足す。新しいテストは、`github/Test/4_実行の高速化/`（新設。`README.md` を作る）に置く。`github/Test/README.md` に、フォルダの行を足す（**足した行だけを自分の変更とし、そのファイルはコミットしない**）。変更をコミットしてから、実験を流す（`github_dirty` = false）。**変更で `github_version` が変わる。T007 は、変更後の版で、864 run を流す**。
8. **実験は、パイロット（数 run、1 位置）だけ。** 864 run の流し直しは、T007 が行う。重い処理を流す前に、`free -g` と `uptime` を確かめる。**サーバーは、約 90% の負荷までは使ってよい**（ユーザーの許可）。
9. **コミット。** 区切りごとに、自分が変えたファイルを名前で指定し、種類で分ける（`github/` の変更＋テスト／ランナー・研究の基盤／実測・文書）。`git -c user.name=yayoten -c user.email=g2222077@tcu.ac.jp commit …`。**push はしない**。他の Claude・ユーザーの未コミットの変更に触らない・巻き込まない。
10. **次のタスクへ。** 全部終わったら、T007（評価の流し直し）を起動する（チェックリスト E）。
