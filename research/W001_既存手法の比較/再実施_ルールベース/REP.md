**V4 の集計の定義。** 3 手法を、48 位置 × エピソード 0〜3（192 セル。1 セル = 1 位置 × 1 エピソード）に置く。各セルの `score_component`（CPA 超過のペナルティ込みの成績）を、手法別に合計する。あわせて次を記録する。

| 量 | 定義 |
|---|---|
| score の合計 | 192 セルの `score_component` の合計（÷20000 の値も） |
| ABid を 1.0 とした値 | その手法の合計 ÷ ABid の合計 |
| セル単位の勝ち負け | 同じセルで、手法 A の `score_component` が手法 B より大きいセルの割合 |
| ペナルティ前の平均報酬 | `reward` のセル平均 |
| ペナルティ係数の平均 | `penalty` のセル平均 |
| 予算消化率 | `budget_consumer_ratio` のセル平均と、0.9 未満のセルの割合 |
| 落札が止まった時刻 | `last_compete_tick_index` が 47 より小さいセルの割合 |
| 順位 | `score_rank`（48 社中）の中央値と、10 位以内のセルの割合 |
| カテゴリ別・エピソード別 | `score_component` の合計が最大の手法 |
| α の時間変化 | ティックごとの `alpha_eff` の中央値（192 セル）と、他の 47 社の α の中央値 |
| 背景の 47 社 | `others_score_mean` のセル平均 |

「Online LP の合計が、PID と ABid の合計の両方より大きいか」も記録する（論文の記述「Online LP が最良」と同じ向きかを見る定義。どちらに転んでも、達成の可否には影響しない）。論文の図 10 の値とは、数値を並べるだけで、一致・不一致の判定はしない（目視の概算しか手元に無いため）。

**V5 の集計の定義。**

| 量 | 定義 |
|---|---|
| 超過したセルの割合 | `penalty` < 1 のセルの割合（実績 CPA > 制約） |
| 超過率の中央値 | `cpa_exceedance_rate` =（実績 CPA − 制約）÷ 制約 の、192 セルの中央値 |
| 超過率が 0.5 を超えたセルの数 | `cpa_exceedance_rate` > 0.5 のセルの数 |
| ペナルティで失った報酬の割合 | 1 − Σ`score_component` ÷ Σ`reward` |
| 実績 CPA ÷ 制約 の中央値 | `real_cpa` ÷ `cpa_constraint` の中央値（平均は、報酬が 0 に近いセルで発散するので使わない） |

### 3.2 結果として使う run の決め方（判定。実験の前に決めた）

**知りたいこと。** DB には、同じ設定・同じ端末（Linux）で流した 144 run が、すでにある。ただし、`github/` の版が今と違う。今のコードの版で流しても同じ結果になるなら、既存の 144 run を、確定した設定での結果として使える。

**手元にある材料。**

| 種類 | 内容 | 出どころ |
|---|---|---|
| DB の事実 | Linux・既定設定・48 位置 × エピソード 0〜3 の 3 手法の run が 144 件ある（`rep` = REP002、`spec_name` = `eval_rule_based` 138 件 ＋ `check_rule_based` 6 件、`github_version` = `0536c690ef…`、すべて ok・dirty でない） | `DB/runs/*/meta.json` を数えた（2026-10-10） |
| コードの事実 | 今の `github/` の版は `5c8436a80a…`（HEAD `8baf2a1`）。`0536c690ef` との差は、`strategy_train_env/run/run_bcq.py` の 1 ファイル（学習関数 `train_bcq_model` に引数 `max_action` を足した。既定は従来の 100） | `git diff 0536c690ef 5c8436a80a` |
| コードの事実 | `run_bcq.py` を読み込むのは、`strategy_train_env/main/main_bcq.py` と自分自身だけ（`grep`）。評価の経路（`run_test`、背景の 47 社の戦略）からは読み込まれない | `grep -rn run_bcq github`。**読んだだけで、実行して確かめてはいない** |
| 過去の結果 | 端末をまたぐと（Windows と Linux）、24 セル中 1 セルで結果が違った | 旧 REP002（6 節、8 節の 8） |
| ユーザーの決定 | 古い版と結果が同じなら、評価を全部やり直さなくてよい | `dashboards/agents/tasks/T003/経緯.md` |

**そこから考えたこと。** コードの差は、評価の経路から読み込まれないファイルにしか無い。だから、今の版で流しても、既存の run と同じ値になると考えられる。ただし、これは読んだだけの推測であり、端末をまたいだときのように、思わぬところで値が変わることもある。そこで、一部のセルを実際に流して確かめる。

**確かめ方。** 今のコードの版で、**3 手法 × 6 位置（0, 8, 16, 24, 32, 40。カテゴリごとに 1 つ）× エピソード 0〜3 = 18 run・72 セル**を流す（`params/check_same_as_old.json`）。同じ手法・位置・エピソードの既存の Linux の run と、`episodes` の数値列を比べる。

**判定の基準。**

| 項目 | 基準 |
|---|---|
| 一致 | 72 セルすべてで、`score_component` の差が 0.0（完全一致）。かつ、`episodes` のほかの数値列（`reward`、`all_cost`、`real_cpa`、`penalty`、`score_rank` など全部）も、差が 0.0 |
| 不一致 | 1 セルでも、どれかの数値列に差がある |
| 比べない列 | 時間・メモリの列（`ticks.bidding_seconds`、`tick_wall_seconds`、`rss_mb`、`runs.sim_seconds` など）。実行のたびに変わるため |

あわせて、`ticks` の `alpha_eff`・`n_won`・`cost`・`reward` の最大の差も記録する（判定には、`episodes` を使う）。

**起こりうる結果と、その先。**

| 結果 | 分かること | 次の一手 |
|---|---|---|
| (a) 72 セルすべて一致 | 確かめた 6 位置では、`0536c690ef` から今の版までのコードの変更は、ルールベースの評価の結果を変えない | 既存の Linux の 144 run を、結果として使う。残り 42 位置は流さない（一致は、6 位置の実測と、コードの差が評価の経路に無いことからの推測、と明記する） |
| (b) 1 セルでも不一致 | コードの変更か、実行のたびに変わる何かが、結果を変えている | 差が出たセル・列を記録する。同じセルを今の版でもう 1 度流し、今の版どうしで一致するかを見る（コードの差か、非決定性かを分ける）。原因がコードの差なら、どの変更かを調べる。**144 run を今の版で流し直し**（`params/eval_rule_based_new.json`、流した 18 run はそのまま使われる）、それを結果として使う |
| (c) run が error になる、または `github_dirty` = true になる | 測定が成り立っていない | error：原因を見る（メモリ不足なら並列数を下げる）。`run_experiment.py` を再実行すると、ok でない run だけ流れる。dirty：`github/` に未コミットの変更がある（他のタスクの作業）。その run は使わず、変更がコミットされるのを待って流し直す。待てないときは、`進捗.md` に書いて止める |
| (d) 今の版どうしでも一致しない（(b) の確認で分かる） | この端末で、評価が決定的でない | V3（再現性）が満たせないので、「未達成」として記録する。差の大きさを測り、ユーザーに報告する。流し直しは、1 回だけ行う |

**流している途中で `github/` の版が変わったとき**（他のタスクがコミットした場合）：run_id が変わり、版が混ざる。使う 144 run は 1 つの版にそろえる（V1）。そろわなければ、新しい版で、この判定をやり直す。

### 3.3 再現性（V3）の確かめ方

判定で流した run のうち、PID・位置 0（今の版）を、`params/repro_pid_p0.json` で `--force` を付けて再実行する。再実行の前に、もとの `episodes`・`ticks`・`agents` を `results/raw/` に写しておき、再実行のあとの値と比べる。
`--force` で上書きされるのは、**このタスクで作った run だけ**である（既存の原本は上書きしない）。

## 4. 取る特徴量と、その理由（仮定）

`ticks`・`episodes`・`agents`・`runs` の列を、そのまま使う（列の定義は `DB/columns.json`）。「理由」は、取る前に置いた仮定で、確かめたものではない。

| 仮定 | 取る量 |
|---|---|
| 手法の違いは、入札係数 α の決め方の違いである | `ticks.alpha_eff`、`alpha_rank`、`alpha_others_median` |
| 成績は、競合の入札水準と、競合がいつ脱落するかに左右される | `ticks.lwc_mean`、`n_active_agents`、`total_cost_all`、`agents` 表 |
| 予算の使い方（ペース配分）が、成績を決める | `ticks.cost`、`remaining_budget_before`、`episodes.budget_consumer_ratio`、`last_compete_tick_index` |
| 落札の質（スロット、露出）で、得られる価値が違う | `ticks.n_won`、`n_slot1/2/3`、`n_exposed`、`episodes.win_pv_ratio`、`second_price_ratio` |
| 成績に、CPA 制約のペナルティが大きく効く | `episodes.real_cpa`、`penalty`、`cpa_exceedance_rate`、`reward` |
| 位置（予算・CPA 制約・カテゴリ）による有利不利がある | `episodes.budget`、`cpa_constraint`、`category`、`runs.player_index` |
| 規模感を知るには、時間とメモリが要る | `runs.sim_seconds`、`peak_rss_mb`、`bidding_seconds_per_call_mean`、`ticks.bidding_seconds` |
