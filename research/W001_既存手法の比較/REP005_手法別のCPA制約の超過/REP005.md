## 1. 確認したい現象（仮説は立てない）

**既存 8 手法で、CPA 制約の超過は、どの手法で、どれだけ起きているか。**

## 2. 達成とみなす条件（集計の前に決める）

次をすべて満たしたとき「達成」とする。多い・少ないの判断は、付けない。

| 番号 | 条件 |
|---|---|
| S1 | 8 手法のそれぞれについて、192 セル（48 位置 × エピソード 0〜3）がすべて揃っている。使う run は、すべて `status = ok`、`github_dirty = false` である |
| S2 | 全セルが、下の 4 つの区分のどれか 1 つに入り、手法ごとの合計が 192 になる |
| S3 | 購入数が 1 以上の全セルで、DB の `cpa_exceedance_rate` が、`all_cost ÷ reward ÷ cpa_constraint − 1` と一致する（差の絶対値が 1e-6 以下） |
| S4 | 下の「記録する量」が、8 手法すべてについて、表と図に記録されている |

**セルの区分**（1 セル = 手法 × 位置 × エピソード）

| 区分 | 定義 |
|---|---|
| 超過 | 購入数が 1 以上で、実績 CPA が制約より大きい |
| 制約内 | 購入数が 1 以上で、実績 CPA が制約以下 |
| 購入 0・支払いあり | 購入数が 0 で、支払いが正。実績 CPA が定義できない |
| 購入 0・支払いなし | 購入数が 0 で、支払いも 0（落札していない） |

- 実績 CPA = 支払いの合計 ÷ 購入数（`episodes.all_cost ÷ episodes.reward`）。
- 超過率 = 実績 CPA ÷ 制約 − 1。
- 環境のスコア式は、購入 0・支払いありのセルにもペナルティを掛ける（成績は 0 のまま）。この REP では、「超過」には含めず、別に数える。

**記録する量**

| 量 | 定義 |
|---|---|
| 区分ごとのセル数と割合 | 手法ごと。分母は 192 |
| 超過したセルの割合のエピソード別の値 | 手法ごとに、エピソード 0・1・2・3 の 4 つの値（分母は 48）。ばらつきの目安 |
| 超過率の分位点 | 手法ごとに、購入数が 1 以上のセルの 10・25・50・75・90% 点 |
| 超過の大きさの区間別のセル数 | 超過したセルを、超過率 0〜0.1、0.1〜0.25、0.25〜0.5、0.5〜1、1 超の 5 つに分ける（各区間は下端を含まず、上端を含む） |
| ペナルティ係数 | 手法ごとの平均と、超過したセルだけの中央値 |
| ペナルティで失った報酬の割合 | 1 −（score_component の合計 ÷ reward の合計）。手法ごと |
| 購入数 | 手法ごとの、1 セルの購入数の 10・50・90% 点 |

## 4. 取る量と、その理由（仮定）

「理由」は、取る前に置いた仮定で、確かめたものではない。

- **区分を 4 つにする理由。** 購入数が 0 のセルは、実績 CPA が定義できない。「超過」に入れると、ほとんど落札しない手法（REP002 の CQL、TD3_BC）が、超過の多い手法に見えるおそれがある。
- **超過の大きさの分布を取る理由。** 同じ「超過したセルの割合」でも、少しだけ超えるセルが多いのか、大きく超えるセルが一部にあるのかで、次に立てる問いが変わると考えた。
- **エピソード別の値を取る理由。** 192 セルは、4 つのエピソードの寄せ集めである。手法の間の差が、エピソードの間の差より大きいかを、目で確かめるため。
- **購入数を取る理由。** 購入数が少ないセルでは、実績 CPA が 1 件の購入で大きく動く。超過率を読むときの前提として要る。
