# REP002 学習ベース手法のベースライン

親：W001（作業。問いは未確定）　型：探索　日付：2026-10-08　状態：検証中（実験前の記録）

## 1. 確認したい現象（仮説は立てない）

既存の学習ベース入札手法が、このシミュレータでどう動くかを知り、ルールベース（REP001）と並べた**ベースライン**を作る。
REP001 では、約80GBの学習データが手元になく、学習ベース手法を扱えなかった。今回は公開データを取得して、学習からやり直す。
手法ごとの成績を事前に予想できる材料がないので（学習ベースを自分で学習して評価したことがない）、探索にする。

知りたいこと（番号は、下の達成条件と結果の対応に使う）。

- L1 データ。公開データ（21 日分）を欠けなく取得でき、学習データ（1 行 = 広告主 1 社 × 1 ティック）を作れるか。
- L2 学習。5 手法を、本家の既定設定のまま学習できるか。どれだけ時間がかかるか。同じ条件で同じ重みになるか。
- L3 評価。学習した重みを、48 社のどの位置に置いても、最後まで走るか。
- L4 ベースライン。8 手法（ルールベース 3 ＋ 学習ベース 5）を同じ端末・同じコードで並べると、成績はどう並ぶか。
- L5 学習の条件への感度。学習ステップ数、乱数シード、重みの出どころ（自前／同梱）で、成績はどれだけ動くか。
- L6 特徴量。後の考察に使う量を、欠損なく取れているか。

## 2. 達成とみなす条件（実験の前に決める）

次をすべて満たしたとき「達成」とする。

| 番号 | 条件 |
|---|---|
| L1 | `Test/2_学習データと学習手法/` の test_01・test_02 が全件通る（21 日分、欠損なし、48 社 × 約 50 万 PV、学習データ 21 × 48 × 48 行） |
| L2 | この REP の全モデルが status=ok で、損失が最後まで有限である。既定設定の 5 モデルは、学習し直すと重みの SHA-1 が一致する（test_05） |
| L3 | この REP の全 run が status=ok で、score が有限である |
| L4 | 8 手法の、192 セル（48 位置 × エピソード 0〜3）の score 合計・ABid を 1.0 とした値・順位が記録されている（判断は付けない） |
| L5 | 下の 3 つの追加条件の成績と、既定設定に対する比が記録されている（判断は付けない） |
| L6 | この REP の run の `episodes`・`ticks`・`agents` の全数値列に、NaN・無限大がない |

**L4 の集計の定義。** 手法ごとに、既定設定（学習ベースは「本家の既定のステップ数・seed=1 で自前学習した重み」）の run を、48 位置 × エピソード 0〜3 に置く。
各セルの `score_component`（CPA 超過ペナルティ込み）を手法別に合計する。あわせて、REP001 と同じ量（ペナルティ前の平均報酬、ペナルティが掛かったセルの割合、
CPA 超過率の中央値、予算消化率、順位の中央値）を記録する。論文の図10（目視の概算：Online LP 6.5〜7、DT 4.5、IQL 2.6〜3、PID 2.3〜3.5、BC 2.3〜2.5、Abid 0.4〜1）とは、
同じ「ABid を 1.0 とした値」を並べて記録するだけで、一致・不一致の判定は達成条件に含めない。

**L5 の比の定義。** 位置 0, 8, 16, 24, 32, 40 × エピソード 0〜3（24 セル）の `score_component` の平均を、同じ手法・同じ 24 セルの既定設定の平均で割る。

## 3. 実験の条件

| 項目 | 内容 |
|---|---|
| 公開データ | `github/pre_generated_dataset/readme_dataset.md` の zip 11 本（period-7〜27 の 21 日分、展開後 約77GB）。取得は `Test/2_学習データと学習手法/download_data.sh` |
| 学習データ | 本家の `TrainDataGenerator._generate_train_data` を period ごとに呼び、period の昇順に結合（`research/src/make_train_data.py`）。48,384 行。状態 16 次元、行動 = そのティックの α、報酬 = 露出した PV の価値の和（本家の既定。CPA ペナルティは入らない） |
| 学習 | 本家の `run_{bc,iql,cql,bcq,td3_bc}.py` の学習関数を、データの場所・保存先・ステップ数だけ渡して呼ぶ（`research/src/train_model.py`）。ハイパーパラメータは本家の既定のまま。バッチ 100。乱数は `random`・numpy・torch を seed で固定。CPU |
| 既定のステップ数 | BC 20000、IQL 20000、CQL 100、BCQ 100、TD3_BC 100（本家のコードの値） |
| 評価の環境 | REP001 と同じ：`github/config/test.gin` の既定、プレイヤーを 48 社の 1 社に置き換え、残り 47 社は同梱の戦略のまま。`seed=1` |
| 比較（L4） | 学習ベース 5 手法（既定設定の自前の重み）× 48 位置 × エピソード 0〜3 = 240 run。ルールベース 3 手法（既定）× 48 位置 = 144 run も、この端末で流し直す（下の理由） |
| 追加 1：同梱の重み（L5） | 5 手法 × 位置 0,8,16,24,32,40 = 30 run。シミュレータに同梱の学習済み重み（`official_agent/`）をプレイヤーに使う |
| 追加 2：学習ステップ数（L5） | CQL / BCQ / TD3_BC を 20000 ステップ（BC・IQL と同じ長さ）で学習した重み × 6 位置 = 18 run。既定の 100 ステップが、他の 2 手法の 1/200 と短いため |
| 追加 3：乱数シード（L5） | 5 手法 × seed 2, 3（既定のステップ数）で学習した重み × 6 位置 = 60 run。学習の乱数で成績がどれだけ動くかを見る |
| 実行 | `research/src/run_experiment.py`、8 並列以内。Linux（Ubuntu、16 コア、32GB）/ Python 3.9.16 / torch 1.12.0+cu102 を CPU で使用 |
| 記録 | 学習は `DB/models/<model_id>/`（条件・重み・損失）、評価は `DB/runs/<run_id>/`。`runs.model_id` で結ぶ |

**ルールベースを流し直す理由（実験の前に確かめたこと）。** REP001 は Windows で実行した。この端末で位置 0・24 の 3 手法（6 run、24 セル）を流して
REP001 の記録と比べたところ、23 セルは報酬・score が一致したが、ABid・位置 0・エピソード 0 だけ、購入数が 26（Windows）と 24（Linux）で違った
（`params/check_rule_based.json`）。端末をまたぐと完全には一致しないので、8 手法を同じ端末・同じコードの版で並べる。

**追加 2 の打ち切りの決まり。** 20000 ステップの学習が、1 モデルで 2 時間を超える見込みの手法（100 ステップの所要時間から見積もる）は、追加 2 から外し、外したことを 10. に記録する。

**対象外。** DT（シミュレータ側に戦略が無い）、MOPO・COMBO（学習コードがリポジトリに無い）。ユーザーと決めた（2026-10-08）。

## 4. 取る特徴量と、その理由（仮定）

評価の特徴量は REP001 と同じ（`ticks`・`episodes`・`agents`。理由は REP001.md の 4.）。学習ベースで足すものは次のとおり。
「理由」は取る前に置いた仮定で、確かめたものではない。

**仮定1：学習ベースの成績は、学習データの中の行動（誰が、どんな α で入札していたか）に左右される。**
- `DB/train_data/period-N.json`：広告主ごとの予算・CPA 制約・平均の α・最初のティックの α・支払い・購入数・実績 CPA。
  学習データが、どんな手法の記録の混ざりなのかを知るため。

**仮定2：学習が足りているか／発散していないかで、成績が変わる。**
- `DB/models/<model_id>/loss.csv`（1 ステップごとの損失）、`models.loss_last10pct_mean`、`loss_all_finite`、`step_num`。
  既定の 100 ステップが短すぎないかを見るため。

**仮定3：学習の乱数で、重みと成績がぶれる。**
- `models.seed`、`model_sha1`。シードを変えた重みの成績の幅を、手法間の差と比べるため。

**仮定4：学習ベースは、状態にも報酬にも CPA 制約を持たないので、CPA 超過のペナルティを受けやすい。**
- `episodes.real_cpa`、`penalty`、`cpa_exceedance_rate`、`budget_consumer_ratio`（REP001 と同じ列）。
- `ticks.alpha_eff`、`alpha_others_median`：学習ベースが出す α の水準と時間変化。

**仮定5：研究の規模感には、学習の時間も要る。**
- `models.train_seconds`、`runs.sim_seconds`、`bidding_seconds_per_call_mean`。

**再現のための記録。** 学習データの SHA-1、重みの SHA-1、乱数シード、実行コミット、`github/` の版、端末・ライブラリの版。

## 10. 未確認事項（無人で進めたときの記録）

実験の前に分かっていたこと・置いた仮定：

- **GPU を使わず CPU で学習・評価する。** ロックの `torch==1.12.0`（Linux の PyPI 版は CUDA 10.2）は、この端末の RTX 3090 で CUDA の計算が落ちる。
  CUDA 11 版の torch に入れ替えれば GPU を使えるが、依存のロックと REP001 の条件（CPU）から外れるので、入れ替えなかった。
- **学習の乱数を 3 つとも固定した。** 本家の `main_*.py` は torch と numpy だけを固定し、`ReplayBuffer` が使う `random` は固定していない。
  本家の手順そのままだと学習のたびに重みが変わるので、`random` も固定した。本家の手順で得られる重みと同じ値にはならない。
- **CQL / BCQ / TD3_BC の既定の 100 ステップは、本家のコードの値をそのまま使う。** 意図した値か、試験用に短くした値が残ったものかは分からない
  （同梱の重みが何ステップで学習されたかも分からない）。追加 2 で 20000 ステップも見る。
- **同梱の BCQ の重みと、学習コードが保存する BCQ は、`forward` の引数が違う。** 同梱の重みは、このリポジトリの学習コードとは別の版で作られた可能性がある。
  戦略側を、両方呼べるように直した（コミット `d19c656`）。
- **学習時と推論時で、状態の正規化の式がわずかに違う**（学習は分母に +0.01）。本家のまま、直していない。
- **推論側の「直近 3 ティック」の特徴量 5 つが、ティック 0〜2 の平均を見ているように読める**（`chat_with_claude/1_既存手法.md` の 13.）。
  学習データ側は直近 3 ティックなので、学習と推論で入力がずれている可能性がある。ベースラインとして本家のままにし、直していない。
- **公開データがどの手法の記録か（背景の 48 社の構成）は、確認していない。** 予算・CPA 制約・カテゴリの並びは、シミュレータの 48 社と同じである（test_01）。
  period 7〜13 は、各カテゴリの先頭の最初の α が 15 で、シミュレータの並び（先頭が PID）と合う。period 14 以降は、先頭の最初の α が 15 でない日が多く、
  どの位置にどの手法がいるかが、日によって違う（test_02。学習データを作ったあと、学習の前に分かった）。
- **公開データの 3 日分（period 9・13・27）に、入札額（`bid`）が NaN の行がある**（計 62,153 行、全体の約 0.01%。ティック 46・47、広告主 1〜3 社。その行は落札も支払いもしていない）。
  本家の学習データの生成は NaN を 0 に置き換えるので、その広告主・ティックの行動（α）は 0 になる（48,384 行のうち数行）。本家のまま、取り除いていない。
- REP001 の結果（Windows）とは、端末が違う。この REP の中の比較は、すべてこの端末で流した run だけで行う。
