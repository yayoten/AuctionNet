# claudeの回答1

## 1. 一言でいうと

「**1日分の広告オークションを、48社が同時に戦うシミュレータ。そのうち1社を自分の入札手法に差し替え、1日の成果（購入数）とペナルティを測る**」実験である。

登場するものは次の4つ。

| もの | 中身 |
|---|---|
| 1日（エピソード） | 広告機会（PV）が約50万回来る。48個の時間枠（ティック）に分けて進む |
| 広告主 | 48社（6カテゴリ × 8社）。それぞれ予算と CPA 制約を持つ |
| プレイヤー | 48社のうち、自分の手法に差し替えた1社 |
| 成績（score） | プレイヤーの購入数に、CPA 制約を超えたときのペナルティを掛けたもの |

## 2. シミュレータの世界

設定は `github/config/test.gin` と `Controller.py`。

- **1エピソード = 1日。** 48ティックに分かれる。1日の PV 数は合計 500,000（`PVNUM`）。ティックごとの PV 数は一定ではなく、基準の比率（最小 0.3%、最大 3.8% ほど）をエピソードごとに揺らして決まる。つまり、**時間帯によって来る広告機会が10倍ほど違う**。
- **PV** = 広告を出せる1回の機会（ページ表示）。
- **価値（pValue）** = その PV に広告を出したとき購入に至る確率（オーダーは 0.0005 前後）。**広告主ごとに別の値**で、同じ PV でも48社が48通りの価値を持つ。`pValueSigma` はその予測の不確実性（ばらつき）。
- **広告主48社**は、位置（0〜47）ごとに予算と CPA 制約が固定されている。
  - 予算：2000〜4850
  - CPA 制約：60〜130（「購入1件に払ってよい上限」）
  - カテゴリ：位置 // 8 で決まる（0〜5）
  - 位置 0, 8, 16, 24, 32, 40 は、各カテゴリの先頭で、**既定では PID が入っている位置**。
- **他の47社の手法**：PID、IQL、TD3_BC、OnlineLP（2種）、CQL、BC、MOPO など（カテゴリの偶数・奇数で構成が少し違う）。**プレイヤー以外の47社は、手法も予算も固定**。

## 3. オークションの仕組み（1つの広告機会ごと）

`BiddingEnv.simulate_ad_bidding` と `run_test.py`。1つの PV について、次の順に進む。

1. **48社全員が入札額を出す。** 予算が残り 0.1 未満の社は 0 で入札する。
2. **入札額の上位3社が、3つの広告枠（スロット1〜3）を得る。**
3. **支払いは「次点の入札額」。** スロット1の勝者は2位の入札額、スロット2は3位、スロット3は4位の入札額を払う。自分の入札額そのものを払うわけではない（だから、入札を上げても支払いが同じだけ増えるとは限らない）。
4. **露出するかは確率で決まる。** スロット1は確率 1.0、スロット2は 0.8、スロット3は 0.6。スロット2が露出しなかったら、スロット3も露出しない。**露出しなければ、支払いも成果も 0**。
5. **露出したら、購入が起きるかを確率で抽選する。** 確率は価値（pValue）に、不確実性（sigma）ぶんのノイズを加えたもの。起きたら成果 1。
6. **予算の上限。** そのティックの支払いが残り予算を超えるなら、超えた割合ぶんの落札をランダムに取り消して、やり直す。予算は超えない。

※ 補足：50万 PV × 3枠で、落札は最大150万回（48社の合計）。支払いが発生するのは露出したときだけで、期待では1 PV あたり 1.0 + 0.8 + 0.48 = 2.28 回、1日で約114万回（コードの規則からの計算で、実測していない）。予算が尽きた社は入札しなくなるので、後半はさらに減りうる。

ここで大事なのは、**エージェントが決められるのは「入札額」だけ**で、露出・購入は環境の乱数と価値で決まることである。

## 4. 入札手法は何を決めるのか

各ティックの頭に、手法の `bidding()` が呼ばれる。受け取るのは、そのティックの全 PV の価値（数万〜数十万個）と、過去の履歴。返すのは、**PV ごとの入札額**。

3手法はどれも、入札額を「**α × 価値**」の形で出す（ABid だけ、価値の2乗を使う）。論文の整理では、価値が PV ごとの違いを受け持つので、**手法の違いは α（入札係数）の決め方の違いにすぎない**。α が大きいほど強気で、多くの PV を落札する。

> α の意味：購入1件を得るのにかけてよい広告費の上限、と考えればよい。α = 70 なら、購入確率 0.001 の PV に 0.07 まで入札する。

## 5. 3手法のしくみ

コードは `github/simul_bidding_env/strategy/` にある。

### PID（`pid_bidding_strategy.py`）

予算のペースを見て、α を上げ下げする。

- ティック0：α = 15（`base_action`）。
- 以降、毎ティック、`x = 前のティックの支払い × 残りティック数 ÷ 残り予算` を計算する（今のペースが続いたら、残り予算の何倍使うか、の目安）。
  - `x < 0.7`（`low_threshold`）：使いが足りない → α × 1.2（`up_factor`）
  - `x > 1.1`（`high_threshold`）：使いすぎ → α × 0.7（`down_factor`）
  - それ以外：据え置き
- 入札額 = α × 価値。

コードを読んで確かめた点：**CPA 制約（`self.cpa`）は入札の計算に使われていない**。また、時間帯ごとの PV 数の違いを見込む比率（`exp_tempral_ratio`）は全部 1（平坦）で渡している。

### ABid（`abid_bidding_strategy.py`）

予算も履歴も見ない、固定の形。

- α = `bid_scale` × 自分の CPA 制約 ÷ そのティックの価値の平均
- 入札額 = α × 価値²（= CPA 制約 × 価値 × （価値 ÷ 平均価値））
- 平均的な価値の PV には「CPA 制約 × 価値」を入札し、価値が高い PV ほど強気、低い PV ほど弱気になる。
- `bid_scale`（既定 1.0）で全体を何倍かにできる。

**予算の残りを見ないので、予算が早く尽きやすい**（REP001 では、最終ティックより前に落札が止まったセルが 81%）。

### OnlineLP（`onlinelp_bidding_strategy.py`）

過去の1日の記録から作った**早見表**を引く。

- 早見表（`official_agent/onlineLpTest/episode-{0..6}.csv`）の列：カテゴリ、ティック、`realCPA`、`cum_cost`。1つの（ティック、カテゴリ）につき約 598 行で、`realCPA` の小さい順に、支払いの累計 `cum_cost` が並ぶ。
- 引き方：**今の残り予算を、初めて超える `cum_cost` の行**を探し、その行の `realCPA` を α にする。
  - 例（episode-0、ティック10、カテゴリ0）：残り予算 1000 なら α ≈ 55.6、2000 なら α ≈ 66.7。残り予算が多いほど、α は大きく（強気に）なる。
- 上限：α ≤ CPA 制約 × `cpa_cap_ratio`（既定 1.5）。
- 表が引けなければ、α = CPA 制約。
- どのエピソードの表を使うか（`episode`）は引数で、既定は 0。

つまり、「予算に見合った、コスパのよい PV だけ買う α」を、事前の記録から引き当てている。

## 6. score の計算

`PlayerAnalysis.py`。

1. 1エピソード（1日）ごとに、
   - `reward` = 1日の購入数の合計
   - `real_cpa` = 1日の支払い合計 ÷ `reward`
2. **ペナルティ**：`real_cpa` が CPA 制約 `c` を超えたら、`(c ÷ real_cpa)²` を掛ける。超えなければ 1。
3. エピソードの成績 = ペナルティ × `reward`（DB の `score_component`）。
4. 複数エピソードの成績を足し、20000 で割ったものが、1 run の `score`。

例：予算 2900、CPA 制約 100 の広告主。
- 購入 29 件、支払い 2900 → CPA 100 ちょうど → ペナルティなし → 成績 29
- 購入 20 件、支払い 2900 → CPA 145 → ペナルティ (100/145)² = 0.48 → 成績 9.5

**予算を使い切って購入数を増やしても、CPA が制約を超えれば大きく減点される。** だから Online LP のように、予算を使い切らなくても（消化率 0.75）CPA を守る手法が、高い成績になりうる。

## 7. REP001 の実験の組み方

`research/W001_.../REP001_.../params/*.json` と `research/src/run_experiment.py`。

### 用語

| 用語 | 意味 |
|---|---|
| 位置 | プレイヤーを置く広告主の番号（0〜47）。その位置の予算・CPA 制約・カテゴリを引き継ぐ |
| エピソード | 1日。番号（0,1,2,3）が、広告機会の生成と環境ノイズの乱数シードになる |
| セル | （手法, 位置, エピソード）の1組。REP001 の比較は 3 × 48 × 4 = 576 セル（1手法あたり 192 セル） |
| run | 1手法の設定 × 1位置。エピソード 0〜3 を続けて回す。DB に1件記録される |
| 掃引 | パラメータを1つだけ振り、他は既定のままにする |

### 比較実験（E4）

- 手法 3つ × 位置 48 × エピソード 4 → 144 run（`base_all.json`）。
- 手法はすべて**既定のパラメータ**。
- 同じ位置・同じエピソードなら、手法が違っても、広告機会と他の47社の構成は同じ。

### パラメータ掃引（E5）

- 位置は 6 つ（0, 8, 16, 24, 32, 40。各カテゴリに1つ）。エピソード 0〜3。
- 1つのパラメータだけ振る。

| 手法 | パラメータ | 振った値（既定は太字） |
|---|---|---|
| PID | `base_action`（最初の α） | 5, **15**, 30, 60, 100 |
| PID | `up_factor` | 1.1, **1.2**, 1.5 |
| PID | `down_factor` | 0.5, **0.7**, 0.9 |
| PID | `low_threshold` | 0.5, **0.7**, 0.9 |
| PID | `high_threshold` | 0.9, **1.1**, 1.3 |
| ABid | `bid_scale` | 0.25, 0.5, **1**, 2, 4 |
| OnlineLP | `cpa_cap_ratio` | 1.0, **1.5**, 2.0, 3.0 |
| OnlineLP | `episode`（早見表の日） | **0**, 3, 6 |

- run の数：既定値の点は比較実験と同じ run になるので重複して流さず、既定以外の 21 点 × 6 位置 = 126 run。合計 144 + 126 = **270 run**。

### 固定した条件

- PV 数 500,000、48 ティック、PV 生成は `neuripsPvGen`。乱数シード `seed = 1`。
- 1 run は約 150〜215 秒、メモリ約 2.5GB。8 並列で比較実験が 63 分。
- 結果は `DB/` に、1ティックごとの時系列（α、落札数、支払い、残り予算 など）まで記録する。

## 9. コードを読んで気づいた点（未検証を含む）

質問の材料として挙げる。いずれも、結果を説明できると確かめたものではない。

1. PID は CPA 制約を使わず、ペースだけを見る。それなのに予算消化率が 0.99 で、ペナルティが掛かるセルが 82%。
2. PID の最初の α（15）は、他の47社の中央値（約 68）よりかなり小さい。序盤の落札が遅れる（REP001 の観測）。
3. ABid は予算を見ないので、早く尽きる。一方で `bid_scale` を 0.5 にすると 1.39 倍になる（振った中の最良）。
4. Online LP の早見表が、どの日・どの設定で作られたのか、評価するエピソード（0〜3）と同じ日かどうかは、確認していない（REP001 の未確認事項）。（追記：表の作成コードを読んで、各ティックの表は「そのティック以降の PV だけ」で作られ、累計は 6000 までと分かった。詳細は `1_既存手法.md` の 4 節。元データの出どころは未確認のまま。）
5. 環境のノイズ（露出・購入）は、`BiddingEnv` の中で `default_rng(seed=1)` をその都度作って引いている。コードを読む限り、ティックごとに同じ乱数列の先頭から使う作りに見える。これが評価に影響するかは未検証。
6. 位置 0, 8, …, 40 は、既定では PID が入っている位置。掃引は、PID を別の手法・設定に差し替えたときの結果になる。
