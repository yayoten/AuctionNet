## 4. 集計の定義と、達成とみなす条件（評価の前に決める）

### 4.1 集計の定義

| 量 | 定義 |
|---|---|
| セル | 位置（48）× エピソード（0〜3）= 192 |
| score | セルごとの `score_component`（ペナルティ係数 × 獲得価値） |
| seed ごとの平均 score | その重みの 192 セルの score の平均 |
| 3 seed の平均 score | seed ごとの平均 score の、3 つの平均（＝ 576 セルの平均） |
| seed 間の幅 | （seed ごとの平均 score の最大 − 最小）÷ 3 seed の平均 score |
| 予算消化率 | `budget_consumer_ratio` の平均と最小（seed ごと、3 seed） |
| CPA 制約の達成状況 | 落札したセル（購入数 > 0）のうち、実績 CPA が制約を超えたセル（`cpa_exceedance_rate` > 0）の割合。超過率の中央値。購入数が 0 のセルの数（実績 CPA が定義できない）。ペナルティで失った報酬の割合（1 − Σ score ÷ Σ reward） |
| α の水準 | `ticks.alpha_eff`（実効の入札係数）の、セル内のティック平均の平均。残り予算があるティックに限った値も出す |
| α の動き | セル内のティック間の標準偏差の平均（ティックで動く幅）。ティック 0 の α の、セル間の標準偏差（状態で動く幅） |
| 8 手法の表の score | ルールベースは 192 セルの合計。学習ベースは、セルごとに 3 seed を平均してから 192 セルを合計。ABid を 1.0 とした値も出す |
| セル単位の比較 | 192 セルのうち、その手法（学習ベースは 3 seed の平均）が OnlineLP を上回ったセルの割合 |

score の大小で、設定を選び直すことはしない（設定は確定済み。評価の日の値は、選択に使わない）。

## 8. 未確認事項（無人で進めたときの記録）

評価の前に置いた仮定・迷った点：

- **「デフォルトで登録されているアルゴリズムを全部」の範囲（ユーザーに確認したい）。** 何をもって「登録」とするかで、対象が変わる（3.3 の表）。背景の 48 社の既定の構成で数えると、5 手法のほかに MOPO・COMBO が入る。本家 README の「実装済み」の表で数えると、DT が入り、CQL・MOPO・COMBO は入らない。この REP では、**確定した設定がある 5 手法を主とし、MOPO・COMBO は同梱の重みで参考として評価し、DT は評価しない**とした。5 手法で足りるか、DT を評価できるようにする作業（戦略ファイルと学習の道具の追加、学習の長さの決定）をするかは、ユーザーに決めてほしい。
- MOPO・COMBO を 6 位置でなく 48 位置で流すことにした（同じ 192 セルで 8 手法と並べられるように）。96 run、約 1.5 時間ぶん増える。
- MOPO・COMBO は、`research/src/run_experiment.py`（共有のコード。このタスクの予約の外）を書き換えず、`programs/run_bundled_mbrl.py` の中でだけ戦略の表に足して流す。DB の `runs.strategy` には `MOPO`・`COMBO` と入る。
- ルールベースの run は、「同じ `github_version`」を厳密に取る。旧い Linux の run（`0536c690…`）との差は学習のコード 1 ファイルだけ（2 節）なので、評価の結果は同じになる見込みだが、確かめていないので、同じ版の run でそろえる。
- 4.2 の「10%」は、設定を決めたときの目安を、そのまま読み替えずに使う。この REP の合否ではなく、5 節の場合分けに使うだけである。
- 型は「探索」にした（成果物が、ベースラインの値の記録であり、1 つの仕組みの支持・不支持ではないため）。
