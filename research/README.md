## 1. このフォルダの目的

研究は1本道ではなく、**木**のように広がる。
ある事実Aに対して、仮説B・C・Dが立ち、次に進むのはそのどれかである。検証の結果から、また新しい問いが生まれる。

この木を見失わないように、次の3つを実現する。

- **流れが追える**：何を問い、何を検証し、何が分かり、何がまだ分からないかを、あとから辿れる。
- **着実に進む**：一度に大量のことをせず、**1つの検証に1つの仮説**を立て、クリティカルに確かめる。大きな成果ではなく、小さな検証を積み上げる。
- **構造とフォルダが一致する**：頭の中の問いの木と、ディレクトリの構造を同じ形にする。フォルダを見れば、研究の構造が分かる。

## 2. 基本の考え方

知りたいのは「何％良くなったか」ではなく、**どの説明を検証し、何が分かり、何がまだ分からないか**である。
そのために、次の3つを必ず分けて扱う。

| 区別するもの | 例 | 性質 |
|---|---|---|
| **観測した事実** | 「条件Aでは、運用後も不確実性が残った」 | 実験で見たこと。数値・図表で示せる |
| **事実から考えた仮説** | 「Bとの交絡が、学習を止めている」 | 原因についての推測。まだ確かめていない |
| **検証から言える結論** | 「仮説は支持された／されなかった」 | 判断指標に照らした判断。言える範囲つき |

特に、次のことを守る。

1. **性能の改善と、改善した理由の検証は別物。** 「提案手法が良かった」だけでは、原因についての自分の説明が正しいことにはならない。理由を確かめるには、その理由を直接変える実験が要る。
2. **仮説を支持する結果だけを探さない。** 良くならなかった結果、仮説に反する結果も、成立条件や限界が分かれば成果である。
3. **判断指標は実験の前に決める。** 結果を見てから基準を動かさない。
4. **1つの検証（REP）に1つの仮説。** 複数のことを1本で確かめない。
5. **事実と考察を文で分ける。** 「〜であった」（事実）と「〜と考えられる」（解釈）を、同じ文に混ぜない。

仮説を1文で書けるなら**検証**、書けなければ**探索**にする（無理に仮説を作らない）。探索で見えた現象から仮説が立ったら、次の検証に進む。検証と探索は、行き来してよい。

## 3. 構成要素

研究を、次の4つの要素で管理する。

| 要素 | 何か | 例 |
|---|---|---|
| **大きな問い** | 研究を支える大きな枝。修論の章に対応づける | 「既存手法で損失が大きいのはなぜか」 |
| **小さな問い** | 大きな問いを分けたもの。事実Aから生まれた疑問など。入れ子にできる | 「識別困難が原因なのか」 |
| **検証（REP）** | 仮説を1つ立て、検証する。複数の細かい実験を含んでよい | 「ベースライン既知で形状推定は改善するか」 |
| **探索（REP）** | 仮説がないまま、現象を確認する。動作確認や、仮説を立てるための観察 | 「このシミュレータで何が起きるか」 |

検証と探索は、まとめて **REP**（報告の単位）と呼び、**同じ通し番号**で数える（REP001、REP002、…）。
1つのREPは、1つの問いの下に置く。

事実Aからの流れは、次のように表す。

```
小さな問い「Aはなぜ起きるのか」    ← 事実Aから生まれた疑問
├─ 検証B（仮説B）
├─ 検証C（仮説C）
└─ 検証D（仮説D）
```

仮説B・C・Dは、同じ問いの下に並ぶ兄弟になる。

## 4. IDの付け方

IDは**ASCIIのみ**で、**一度振ったら再利用しない**。外部のツール（Notion など）で評価するときにも、そのまま使える。

| 要素 | 形式 | 例 |
|---|---|---|
| 大きな問い | `Q` + 3桁の通し番号 | `Q001` |
| 小さな問い | 親のID + `-` + 英大文字 | `Q001-A` |
| 小さな問いの中の問い | 親のID + 数字 | `Q001-A1` |
| さらにその中 | 親のID + 英小文字 | `Q001-A1a` |
| 検証・探索（REP） | `REP` + 3桁の通し番号 | `REP001` |

決まりは次のとおり。

- **階層ごとに、文字と数字を交互に使う。** 大文字と小文字だけで区別しない。macOS のファイル名は大文字と小文字を区別しないので、`Q001-A` と `Q001-a` が同じ階層で衝突する。
- **問いのIDは「生まれた場所」を表す。** 問いを別の親の下に移しても、IDは変えない。
- **REPのIDは位置を持たない。** 全体で1本の通し番号で、検証と探索を区別しない。番号の大きさがおおよその時系列になる。
- **他のREPや問いを参照するときは、パスではなくIDで書く。** フォルダを移しても、参照が壊れない。
- 型（検証か探索か）や状態は、IDに入れず、mdの冒頭に書く。

## 5. ディレクトリ構成

```
research/
├── README.md                       # このファイル
├── MASTER.md                       # 最上位の地図（人が書く）
├── flow.md                         # 問いの木（フォルダから自動生成。手で編集しない）
├── src/                            # 自作のコード（make_flow.py、build_summary.py、複数のREPで使う共通コード）
└── Q001_{大きな問いの題}/
    ├── Q001.md                     # この問いの記録
    ├── Q001_まとめ.pdf              # 配下のREPのPDFを並べたもの（作り直せる）
    └── Q001-A_{小さな問いの題}/
        ├── Q001-A.md
        ├── Q001-A_まとめ.pdf
        ├── REP001_{題}/            # 探索または検証
        │   ├── REP001.md           # 作業用の記録
        │   ├── REP001.tex / .pdf   # 1ページの報告
        │   ├── programs/           # この検証の実験コード
        │   ├── fig/                # 報告に載せる図
        │   └── results/            # 実験の結果（重い生データは results/raw/）
        ├── REP002_{題}/
        └── Q001-A1_{さらに小さな問いの題}/    # 問いの中の問い
            └── REP003_{題}/
```

決まりは次のとおり。

- **フォルダ名は `{ID}_{題}`。** IDを先頭に置く。題は日本語でよい。
- **問いのフォルダには、同名のmd（`Q001-A.md` など）を1つ置く。** その問いの背景と、なぜその問いを立てたかを書く。
- **問いは何階層でも入れ子にできる。** 検証・探索（REP）は、問いの直下に置く。
- **フォルダの位置は、ふだん動かさない。** 組み替えるときも、IDは変えない。
- **research/ に置かないもの。**
  - 本家の AuctionNet のコード → `github/`（変更してよい）
  - 会議メモ・会議用の資料 → `MTG/`
  - 論文の翻訳・要約 → `Docs/research_paper/`

## 6. 各ファイルに何を書くか

書式は**固定しない**。必要になったら足す。ここでは、最低限の目安だけ示す。

### 6.1 問いのmd（`Q001.md`、`Q001-A.md`）

冒頭に `status:`（進行中／答えが出た／保留）と `summary:` を書いておくと、`flow.md` に反映される（任意）。

- **背景**：この問いの根拠になった事実（出典のREPのIDつき）。
- **問い**：何を知りたいか。
- **子の一覧**：配下の小さな問いと、REPの一覧（ID、型、1行の要約、判断）。
- **今の状態**：進行中／答えが出た／保留。答えが出ていれば、分かったことを数行で。

### 6.2 REPのmd（`REP001.md`）

作業用の記録。実験の前から書き始め、実験が進むにつれて足す。

- 冒頭：型（検証／探索）、日付、状態（未着手／検証中／支持／不支持／判断不能／達成／未達成）、親の問いのID。
  `flow.md` の生成スクリプトが読むので、mdの先頭に `---` で囲んで、次の3つを書いておくとよい（すべて任意）。
  ```
  ---
  type: 検証            # 検証 / 探索
  status: 検証中        # 未着手 / 検証中 / 支持 / 不支持 / 判断不能 / 達成 / 未達成 / 保留
  summary: 1行の要約
  ---
  ```
- **検証のとき**：仮説（1文）、仮説を作るために使った結果（あれば明記）、予測、判断指標（**実験の前に決める**）、実験の記録（programs、パラメータ、実行コミット、乱数シード）、結果（事実だけ）、判断。
- **探索のとき**：確認したい現象、仮説を立てられない理由、達成とみなす条件（実験の前に決める）、実験の記録、結果、そこから生まれた問い。
- **得られた事実**：解釈を含まない1文で、条件つきで書く。支持されなかった仮説の結果も、条件つきの事実として残す。後の実験で覆ったときは、消さずに「覆った」と理由を書く。

### 6.3 REPの tex / pdf

REPの内容を**1ページ**にまとめた報告。書き方と型（仮説検証型／探索型）の構成は、`.claude/commands/make_progress_report.md` に従う。

### 6.4 MASTER.md

研究全体の最上位の地図。人が書く。次の項目を持つ。

- 最終ゴール
- 研究の範囲（使う環境、扱う問題設定、扱わないこと）
- 大きな問いの一覧（ID、問い、対応する修論の章、状態）
- 現在地（進行中のREP、次の候補、保留中のもの）
- 分かったこと（確立した事実を、REPのIDつきで数行）
- 判断の履歴（方針を変えた日付と理由）

### 6.5 flow.md

フォルダの構成と、各mdの冒頭の情報から、問いの木と各REPの判断を一覧にしたもの。**自動生成し、手で編集しない。**

```bash
python3 research/src/make_flow.py
```

## 7. PDFの作り方と使い方

PDFは2種類ある。どちらも、元は REP の tex。

| PDF | 中身 | 作り方 |
|---|---|---|
| **REPのPDF**（`REP001.pdf`） | 検証または探索1つの、1ページの報告 | REPの tex をコンパイルする |
| **問いのまとめ**（`Q001-A_まとめ.pdf`） | 配下のREPのPDFを、REP番号の順に並べたもの | REPのPDFを結合する |

- **問いのまとめのページ数は、配下の検証・探索の数と一致する。** 1ページに収まらないREPがあれば、その分だけ増える。
- これにより、「この問いに、どんな仮説検証をしてきたか」が、ページをめくるだけで分かる。
- **上位の問いのまとめ**（`Q001_まとめ.pdf`）は、配下のすべての問いをたどって、REPを番号順に並べる。
- **まとめは作り直せる生成物。** 手で編集しない。REPを直したら、まとめを作り直す。

```bash
python3 research/src/build_summary.py Q001-A     # 問いのID、またはフォルダのパス
python3 research/src/build_summary.py --all      # すべての問い
```

REPのPDFがないとき、またはREPの tex より PDF が古いときは、警告を出す。結合には `pdfunite`（poppler）を使う。
- 会議用のPDFは、`MTG/yyyy_mm_dd/` に、その時に必要なREPのページを束ねて作る。（ここでは扱わない。）
- REPのPDFは `/make_progress_report` で作る。IDは `\reportid{REP001}` `\questionid{Q001-A}` で明示的に渡す（自動では振られない）。
- LaTeX は upLaTeX 前提（`pdflatex` は使わない）。手順とテンプレートは `.claude/commands/make_progress_report.md` と `.claude/templates/progress_report/`。

## 8. 実験の回し方

- **`github/` は変更してよい**（不具合の修正、アルゴリズムの追加、設定の変更など）。
  - 変更したら、本家からの差分が追えるよう、変更内容と理由をコミットメッセージに書く。実験の記録には、実行したコミットを残す。
  - パラメータを変えたいときは、コードを書き換えずに済むよう、`params.json` に書いて流し込むのを基本にする。本家の環境設定は gin（`github/config/test.gin`）で、json から gin の上書き指定へ変換して渡す想定。
  - クローン直後にあった不具合（`config/test.gin` が読めない等）は修正済み。修正の一覧と検証は `Test/1_初期セットアップ/README.md`。乱数と PID の修正で、結果の数値はクローン直後と変わっている。
  - `github/` を変えたら、`Test/1_初期セットアップ/` の pytest を回して確認する。
- **実験のコードは、REPの `programs/` に置く。** 共通で使う部分が出てきたら、`research/src/` に出し、`programs/` は、それを呼ぶ薄いスクリプトにする。
- **実験の記録を残す。** 使ったパラメータ（`params.json`）、実行したコミット、乱数シードを、REPのmdか `results/` に残す。あとから同じ結果を再現できるようにするため。
- **重い生データは `results/raw/` に置く**（`.gitignore` 済み）。要約のCSVや図は残す。
- `params.json` には、**変える値だけ**を書く。固定する値は書かない。報告の「検証方法」の表（固定する条件と変える条件）と対応させる。

## 9. 研究の進め方（1サイクル）

1. **問いを決める。** 直前の報告の「今後の展望」と、未解決の問いから選ぶ。必要なら、問いのフォルダとmdを作る（IDは、既存の最大値の次の番号）。
2. **REPのフォルダを作り、REPのmdを書く。** 仮説が1文で書ければ検証、書けなければ探索。**検証なら、仮説・予測・判断指標を、実験の前に書く。**
3. **実験を回す**（`programs/`）。複数に分けてよい。
4. **結果を事実として書く。** 解釈は混ぜない。
5. **判断する。** 判断指標に照らして、「支持された／支持されなかった／まだ判断できない」（探索なら達成／未達成）を書く。どこまで言えるか、何がまだ分からないかも書く。
6. **REPの tex / pdf を作る**（1ページ）。
7. **次の問いを立てる。** 結果から生まれた疑問を、新しい問いとして、適切な親の下に作る。問いの md の子の一覧と、MASTER.md の現在地を更新する。
   あわせて `python3 research/src/make_flow.py` で `flow.md` を作り直す。
8. 問いに答えが出たら、**問いのまとめPDFを作り直し**（`python3 research/src/build_summary.py {問いのID}`）、分かったことを MASTER.md に足す。方針を変えたときは、MASTER.md の「判断の履歴」に日付と理由を書く。

### 書き終えたあとの確認

- [ ] 事実と、解釈・推測が、文で分かれているか（「〜であった」と「〜と考えられる」）
- [ ] 判断指標が、実験の前に書かれたものか。結果を見てから動かしていないか
- [ ] 支持されなかった結果が、隠されずに事実として残っているか
- [ ] 性能の改善だけで、原因の説明が正しいと結論していないか
- [ ] REPは1つの仮説（探索なら1つの現象）に絞られているか
- [ ] IDが、既存の最大値の次か。再利用していないか
- [ ] 他の問い・REPを、パスではなくIDで参照しているか
- [ ] 実験の記録（パラメータ、コミット、乱数シード）が残っているか
- [ ] MASTER.md の現在地・分かったこと・判断の履歴を更新したか

## 10. 具体例

以下は、進め方のイメージを示すための**架空の例**であり、実際の研究内容ではない。

```
Q001_既存手法で損失が大きいのはなぜか/
├── Q001.md                       # 背景：観測した事実A「条件Xでは、損失が大きかった」
└── Q001-A_識別困難が原因か/
    ├── Q001-A.md                 # 事実Aから、識別困難が原因ではないかと考えた
    ├── REP001_環境が動くか/        # 探索：まず動作確認と、挙動の観察
    ├── REP002_ベースライン既知/    # 検証：既知にすると形状推定は改善するか
    └── REP003_事後分布の広がり/    # 検証：REP002で改善しなかった理由の切り分け
```

- REP001は探索。仮説がまだ立たないので、挙動を観察する。
- REP002は検証。「未知のベースラインとの識別困難が、形状推定を妨げている」という仮説を1つ立てる。ベースラインを既知にする実験を、パラメータを変えて複数回し、1本の報告にまとめる。
- REP002で形状推定が改善しても損失が改善しなければ、仮説を見直す。これが次の問い・次の検証（REP003）につながる。
- `Q001-A_まとめ.pdf` は、REP001〜REP003の3ページになる。
