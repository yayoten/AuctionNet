# 記録の一覧（何を、なぜ、どの段で取るか）

実験を流し直さずに済むよう、実験のたびに残す量を増やした（T006、2026-10-10。**記録の形式の版 2**）。
ここには、取る量の一覧、取らない量とその理由、段ごとの容量と時間の実測、ユーザーが決める点を書く。
列ごとの意味・単位・「なぜ取るか」は `DB/columns.json`（元は `DB/make_columns.py`）が正である。ここは、その地図である。

> 3 種類を分けて書く：「実測・テストで確かめたこと」「コードを読んで分かること」「Claude の提案（決定ではない）」。
> 実測は、2026-10-10、Linux x86_64（16 コア・31GB）、`github/` の版 `92b564e`、PV 数 50 万、1 run = 1 位置 × 4 エピソード。

## 1. 記録の段と、容量・時間の実測

段は、spec の `"record"`、または `run_experiment.py --record` で指定する。**既定は standard。** 段は run_id に入らない（結果は同じで、残す量だけが違う）。

| 段 | 残すもの | 1 run のサイズ（実測） | 864 run の見積もり | 記録にかかる時間（実測） | 最大メモリ（実測） |
|---|---|---|---|---|---|
| basic | 表 4 つ（`episodes`・`ticks`・`agents`・`sim_iters`）と `meta.json`・`params.json` | 0.23 MB | 0.2 GB | 2.3 秒 | 2.9 GB |
| **standard（既定）** | basic ＋ `raw/agent_ticks`（ティック × 全 48 社、手法の内部状態）＋ `raw/pv_won`（プレイヤーが落札した機会ごと） | 11.4 MB（10.9〜12.2） | **9.9 GB** | 9.4 秒 | 3.0〜3.2 GB |
| detail | standard ＋ `raw/pv_all`（プレイヤーの全機会。約 200 万行） | 92 MB | 79 GB | 10.0 秒 | 3.1 GB |
| full | detail ＋ `raw/bids_all`（全 48 社の、機会ごとの入札額） | 481 MB | 416 GB | 14.9 秒 | 3.3 GB |

- サイズは、`meta.json` の `files`（各ファイルのバイト数）と `du -sh` で測った。standard は、照合の 18 run（PID・ABid・Online LP × 6 位置）の平均と範囲。basic・detail・full は、PID・位置 0 の 1 run。
- 864 run は、ルールベース 144 ＋ 学習ベース 720（REP006.md 4.2）。**見積もりは、1 run のサイズ × 864。** 学習ベースの run は測っていない（`pv_won` は落札数に比例するので、落札しない CQL・TD3_BC では小さくなる）。
- 記録にかかる時間は、`meta.json` の `hook_seconds_total`。シミュレーション全体は 1 run 約 95〜125 秒（4 並列で 110〜120 秒）なので、standard で約 8%。
- 最大メモリは、版 1 の同じ設定の run で 2.7〜2.8 GB だった。standard で約 0.3 GB 増えた。**並列数は、1 本 約 3.2 GB で見積もる**（これまでは 2.9 GB）。
- **容量の制約（リポジトリ全体で 200 GB）との関係**：今は 107 GB（`du -sh .`）。余裕は約 93 GB、その 6 割は約 56 GB。standard（9.9 GB）は収まる。**detail を全 864 run で取ると 79 GB で、6 割を超える**（合計 186 GB。上限には収まるが、余裕が 14 GB になる）。full は収まらない。→ 7 節。

## 3. 取る量の一覧（観点ごと）

「サイズ」は 1 run あたり。「時間」は、記録にかかる時間への寄与（段ごとの実測の差から見たもの。量ごとには測っていない）。

## 4. 取らない量・取れない量と、その理由

| 量 | 取れるか | 理由 | 代わり |
|---|---|---|---|
| Q 値（学習ベース） | 取れない | 保存されている重み（torch.jit）は、方策（actor）だけ。Q 関数は、同梱の重みにも、`DB/models/` の重みにも入っていない（コードとファイルを見た） | 学習のコードで critic を保存するように直せば取れる（学習のやり直しが要る）。このタスクの範囲外 |
| 抽選に使った乱数の値（一様乱数そのもの） | 取っていない | numpy の `binomial` は、使った一様乱数を返さない。取るには、同じ種の乱数を別に引いて再現する必要があり、「記録のために乱数を引かない」に反する | 抽選の結果（`conversion_draw`・`exposure_draw`）は取った。雑音は、(値 − ①) / σ で、標準化した値に戻せる |
| 48 社全員の、機会ごとの全部の値（①・σ・②・枠・露出・購入） | 全 run では取らない | 1 run で数 GB になり、864 run では容量に収まらない | 入札額だけは full で取れる（481 MB）。①・σ・②・購入の抽選は、**入札に依らず、エピソード番号だけで決まる**（コードを読んだ事実。雑音については test_02 で確かめた）ので、コードから作り直せる。全員のティックごとの集計は `agent_ticks` |
| 背景の 47 社の、やり直しの各回の値 | 取っていない | やり直しの各回は、プレイヤーの値と、全体の値（超過した社の番号、最大の超過率）だけにした | `sim_iters.overcost_agents` に、超過した社の番号がある |
| 入札の履歴（`history_*`）そのもの | 取らない | 各ティックの記録から作り直せる | `pv_all`、`agent_ticks` |
| ティックごとの記録を、量ごとに分けた時間 | 取っていない | 記録の時間は、合計（`hook_seconds`）だけ測った | 段ごとの差（1 節） |
| 学習の記録（損失、重みの途中経過）の拡充 | このタスクでは扱っていない | 指示書の範囲は、評価の実行の記録。学習の記録は `DB/models/`（`loss.csv`、`meta.json`）に既にある | — |
| GPU、ディスクの入出力量 | 取らない | 評価は CPU だけ。書き出しは 1 run 0.3〜1.2 秒で、律速でない | `write_seconds` |
