# make_progress_report

研究の進捗報告（REP1つ＝検証または探索1つ＝1ページ）を、テンプレートに沿って LaTeX で作成し、PDF にする。
仮説検証型と探索型の2つの型を持つ。書き方のルールは、この文書の「ルール」節に従う。
置き場所とIDは `research/README.md` に従う（REPは問いのフォルダの中に作る）。

## 使い方

```
/make_progress_report [検証|探索] [問いのID または REPのID] [題材のメモや結果のパス]
```

例：
```
/make_progress_report 検証 Q001-A research/Q001_xxx/Q001-A_yyy/REP002_zzz/REP002.md
/make_progress_report 探索 Q001
/make_progress_report REP003        # 既にあるREPの報告を書き直す
```

テンプレート一式は `.claude/templates/progress_report/` にある。

| ファイル | 役割 |
|---|---|
| `進捗報告テンプレート.tex` | 1ページ目が仮説検証型、2ページ目が探索型 |
| `progress_report.sty` | 体裁と、`\reportid` `\questionid` `\verification` `\exploration` `\summary` `\hypothesis` `\beginverification` などの命令 |

---

## 実行手順

引数を `$ARGUMENTS` として処理する。

### Step 0: 型の決定

`$ARGUMENTS` に型がなければ、`AskUserQuestion` で確認する。
迷うときは「検証したい仮説を1文で書けるか」を尋ね、書けなければ探索型を勧める（ルール 2 を参照）。

### Step 1: 題材の把握

報告に使う材料（実験条件、結果、図表、前のREPの「今後の展望」。探索型は、REPのmdの「結果から生まれた問い」）を、
`$ARGUMENTS` のパス、REPのmd、会話から把握する。足りない情報は、作り話で埋めずにユーザーへ確認する。

- 仮説検証型で、仮説を作るために**既に見た結果**がある場合は、そのことを明記し、
  仮説を作るために使った結果（観測した事実）と、今回の検証で得る結果を分ける。
- 実験が未実施なら、実験前の章（仮説検証型は目的・仮説・予測・検証方法・判断指標、探索型は目的・対象のアルゴリズム・実験環境・取った特徴量）までを書き、サマリーの3文目は「実験は未実施である」にする。

### Step 2: 出力先とIDの決定

1. 報告は、問いのフォルダの下の `REP{番号}_{短い題}/` に置く（例 `research/Q001_xxx/Q001-A_yyy/REP002_zzz/`）。
   親の問いは、`$ARGUMENTS` の問いのID、または会話から決める。決まらなければユーザーに確認する。
   問いのフォルダが未作成なら、`research/README.md`「5. ディレクトリ構成」「6.1 問いのmd」に従って先に作る。
2. REPの番号は、検証と探索を通した連番。`research/` 以下の既存のREPフォルダ（`REP*_*`）から最大の番号を探して +1 する。
   既にあるREPの報告を書き直すときは、そのREPの番号を使う。
3. ファイル名は `REP{番号}.tex`（PDFは `REP{番号}.pdf`）。mdは `REP{番号}.md`（作業用の記録。この報告の元になる）。
4. `research/` の外（`MTG/` など）には、報告を作らない。会議用のPDFは、REPのPDFを束ねて別に作る。

### Step 3: .tex の作成

1. `.claude/templates/progress_report/進捗報告テンプレート.tex` を、Step 2 のパスに `REP{番号}.tex` としてコピーする。
2. **使わない型のページを削除する**（1ファイル＝1報告）。`\clearpage` と、もう一方の型のブロックも消す。
3. `\reportid{REP{番号}}`、`\questionid{問いのID}` を書く（例 `\reportid{REP002}`、`\questionid{Q001-A}`）。IDは自動では振られない。
4. `\verification{}` または `\exploration{}`、`\reportdate{}`（今日の日付、yyyymmdd）、`\summary{}`、各章の本文を、ルールに従って書く。
   テンプレートの説明文は、すべて実際の本文で置き換える。説明文を残さない。
5. 図は `fig/` に置き、`\includegraphics{fig/...}` で読み込む。
6. REPのmdがあれば、その内容を元にする。mdと食い違う内容を書かない。

### Step 4: コンパイル

REPのフォルダで、次を実行する。`.sty` はコピーせず、`TEXINPUTS` で `.claude/templates/progress_report/` を参照する。
リポジトリのどこから呼んでも動くよう、`git rev-parse --show-toplevel` で絶対パスにする。
`ujarticle` は upLaTeX 前提なので、`pdflatex` は使わない。

```bash
cd research/{問い}/.../REP{番号}_{題}
export TEXINPUTS="$(git rev-parse --show-toplevel)/.claude/templates/progress_report//:"
uplatex -interaction=nonstopmode REP{番号}.tex
uplatex -interaction=nonstopmode REP{番号}.tex
dvipdfmx REP{番号}.dvi
rm -f *.aux *.dvi *.log
```

エラーや Overfull/Underfull の警告が出たら直す。

**Windows（MiKTeX）の場合**：`TEXINPUTS` は Windows 形式のパスで、区切りはセミコロンにする
（`export TEXINPUTS="$(cygpath -m "$(git rev-parse --show-toplevel)")/.claude/templates/progress_report//;"`）。
日本語フォントは dvipdfmx が自動で埋め込む。

**PDFの見た目の確認**：PDFをページごとに画像にして、実際に目で見る（日本語の表示、2段組みで図が小さすぎないか、
表のはみ出し、ページ数）。Windows では poppler（`pdftoppm`）が日本語を描画できないので、PyMuPDF で画像にする。

```python
import fitz
d = fitz.open("REP{番号}.pdf")
for i, p in enumerate(d): p.get_pixmap(dpi=75).save(f"page{i+1}.png")
```

2段組みでは、時系列・多数の小図を含む図は、1段（`figure`）だと文字が読めなくなる。2段抜き（`figure*`、`[t]`）にする。

### Step 5: 確認と報告

1. PDF のページ数を確認する。1ページが目標、多くても2ページ。超えたら、簡潔でよい章から削る。
2. 「ルール 5. 書き終えたあとの確認」のチェックリストを1つずつ確認する。
3. 次を報告する。
   - 作成した .tex と PDF のパス
   - 報告の型と、付けたID（REPのID、親の問いのID）
   - 判断（仮説検証型なら「支持された／支持されなかった／まだ判断できない」、実験前なら未実施）
   - 確認できなかった点、ユーザーに確認したい点
4. 問いのまとめPDFと flow.md は、このコマンドでは作らない。必要なら `research/README.md`「9. 研究の進め方」の7・8に進む
   （`python3 research/src/build_summary.py {問いのID}`、`python3 research/src/make_flow.py`）。

# ルール

進捗報告で伝えたいのは「何％良くなったか」ではなく、どの説明を検証し、何が分かり、何がまだ分からないかである。
以下のルールは、人が書くときも、Claude が代筆するときも守る。

## ルール 0. 目的と基本の考え方

進捗報告で伝えたいのは「何％良くなったか」ではなく、**どの説明を検証し、何が分かり、何がまだ分からないか**である。
そのために、次の3つを必ず分けて書く。

| 区別するもの | 例 | 性質 |
|---|---|---|
| **観測した事実** | 「条件Aでは、運用後も不確実性が残った」 | 実験で見たこと。数値・図表で示せる |
| **事実から考えた仮説** | 「Bとの交絡が、学習を止めている」 | 原因についての推測。まだ確かめていない |
| **検証から言える結論** | 「仮説は支持された／されなかった」 | 判断指標に照らした判断。言える範囲つき |

特に次の2点を守る。

1. **性能の改善と、改善した理由の検証は別物である。** 「提案手法が良かった」だけでは、
   「原因についての自分の説明が正しい」ことにはならない。理由を確かめるには、その理由を直接変える実験が要る。
2. **仮説を支持する結果だけを探さない。** 良くならなかった結果、仮説に反する結果も、成立条件や限界が分かれば成果である。

式は仮説の根拠であって、検証の結果ではない。「〜という式が成り立つ」ことは、原因が実際にそうであることまでは証明しない。

## ルール 1. 運用ルール

- **1回の報告＝1つの検証（または探索）＝1つの仮説＝1ページ。** 目標は1ページ、多くても2ページ。
  大きな成果ではなく、着実な進捗を積む。複数のことを1本で確かめない。
- **REPごとに単体のPDFを作る。** 複数のREPをまとめた「問いのまとめ」は、REPのPDFを結合して作る（`research/src/build_summary.py`）。
  1つのtexに複数の報告を入れる場合だけ、各報告の先頭で `\beginverification` を呼ぶ（改ページし、章・図表の番号が戻る）。
- **IDは検証と探索で通し番号（REP001、REP002、…）。** IDは `\reportid` で明示的に書く（自動では振られない）。
  型の順序は自由で、検証→探索→検証のような流れもありうる。
- **報告の最後は、次の報告への接続にする。** 報告の「今後の展望」（探索型の報告には、この節を置かない。次に知りたいことは、REPのmdの「結果から生まれた問い」に書く）が、
  次の報告の「目的」に対応する。仮説と仮説を対応させるのではない。次の報告の目的は、前の報告の展望のどれを受けたものかが
  分かるように書き出す。現象から対策へ一足飛びに進まず、「どこで起きるか」「なぜ起きるか」「原因を除くと変わるか」を1つずつ挟む。
- **判断指標は実験の前に決める。** 結果を見てから基準を動かさない。
- **条件は表で書く。** 固定する値と変える値を分け、文章や箇条書きに埋めない。表のセルは短く書く（ルール 4）。
- 再実験をしない場合は、過去の結果を使ってよい。ただし、その検証の時点でまだ得ていなかった結果は載せない。

## ルール 2. 型の選び方

| 型 | 使う場面 | テンプレートの位置 | 見出し |
|---|---|---|---|
| 仮説検証型 | 検証したい仮説を1文で書ける | 1ページ目（`\verification`） | REP{番号} 検証：題 |
| 探索型 | 仮説がない。動くか確認したい／対象が新しすぎて仮説が立たない／仮説を立てるために現象を見たい | 2ページ目（`\exploration`） | REP{番号} 探索：題 |

迷ったら、仮説を1文で書いてみる。書けなければ探索型で始める。無理に仮説を作らない。
探索型で見えた現象から仮説が立ったら、その現象を次の検証の「観測した事実」に引き継ぐ。型は報告ごとに選び、検証→探索→検証のように行き来してよい。

## ルール 3. 仮説検証型：章ごとの書き方

詳しさの目安：**簡潔**＝1〜2文か表。**丁寧**＝筋道が追えるまで書く。

### サマリー（枠）

2〜3文の平文。1文目に検証した仮説、2文目に検証方法、3文目に結果と判断。数字を入れる。
未実施なら3文目は「実験は未実施である」。タイトルは、知りたいことを問いの形にする。

### 1 目的（簡潔）

何を明らかにしたいかを1〜2文。手法の性能ではなく、**どの説明を確かめるのか**だけを書く。観測した事実は 2.1 に書き、ここには書かない。
前の報告がある場合は、その今後の展望のどれを受けた目的かが分かるように書き出す。

### 2 実験前に考えた仮説

#### 2.1 観測した事実（簡潔）

- 仮説の根拠になった事実だけを書く。条件・図表・数値をそのまま載せる。
- **解釈・考察は書かない。**
- 前の報告から引き継いだ事実には、そのREPのID（例 REP002）を付ける。
- 最初の検証など、前提となる事実がなければ「これまでに観測した事実はない」とだけ書く。

#### 2.2 事実から考えた仮説（**最も丁寧**）

次の3段で書く。

1. **知りたいこと**を平文で書く（何についての事実を、何として知りたいのか）。
2. 枠の中に **仮説を1つ、1文で**書く（`\hypothesis{}`）。
3. 枠の下に、**なぜそう考えたか**を、論文の本文のような文章で書く。「理由：」のようなラベルは付けない。

仮説の書き方：

- 仮説は「知りたいこと」への答えの形にする。原因を知りたいなら「原因には〜が含まれる」。
- 主語と述語を入れ、比べるものをそろえる。
- 原因の数を断定しない（「原因は2つある」と書くと、それ以外がないことまで示す必要が出る）。
- 実験の前に妥当な説明ができないこと（どちらが主な原因か、など）は仮説に入れない。
- 仮説の否定にすぎないものや、計算の誤差の確認は仮説にしない。
- 仮説は1つに絞る。

「なぜそう考えたか」の書き方：

- **事実と、そこから推測したことを、文を分けて書く。**「〜であった。このことから、〜ではないかと考えた。」
- 式は根拠として使ってよいが、「式が示すのは〜までであり、〜は示さない」と範囲を明示する。
- **同じ事実を説明できる別の原因が実際にあるときだけ**、その説明と、それが正しい場合に結果がどうなるかも書く。
  実際にない別の説明を、形だけ挙げない。

#### 2.3 仮説に基づく予測（やや丁寧）

何を変えると、何がどう変わるはずかを、**実験の前に**書く。
仮説が正しいなら**同時に変わるはずの量**も挙げる（最終的な性能だけでなく、その途中の量）。
途中の量が変わるのに性能が変わらなければ、仮説を見直す手がかりになる。

### 3 実験

#### 3.1 検証方法（簡潔）

固定する条件と、変える条件を、表で書く。結果はここに書かない。

#### 3.2 判断指標（**丁寧**）

- 測定する量を挙げる。最終的な性能だけでなく、予測で挙げた途中の量も含める。
- 「支持された」「支持されなかった」「まだ判断できない」のそれぞれが、**どの結果に当たるか**を数値や向きで書く。
- **仮説を支持しない結果**を明記する。
- 実験の後に決めた基準は書かない。

### 4 結果（簡潔）

- **観測した事実だけ**を書く。3.2 の測定量を、同じ順に並べる。
- 原因の説明、評価の言葉（「優れている」「効果的」など）は書かない。
- 数値は、表や図とあわせて示す。

### 5 考察（**最も丁寧**）

最初に、3.2 の判断指標に照らして **「支持された」「支持されなかった」「まだ判断できない」のいずれか**を書く。続けて次を書く。

- **どこまで言えるか。** 結果から言えることと、言えないこと。
- **同じ結果を説明できる別の説明は何か。**
- **何がまだ分からないか。**
- 仮説が支持されなかった、または途中の量だけが変わって性能が変わらなかったときは、**仮説そのものを見直す**。
  追加の仮説を並べて説明して終わらせない。

**文体で事実と考察を分ける。**

| 内容 | 使う文末 |
|---|---|
| 結果から確かに言えること | 「〜であった」「〜が示された」「〜は観測されなかった」 |
| 私の解釈・推測 | 「〜と考えられる」「〜の可能性がある」「〜ではないか」 |

1つの文に、事実と解釈を混ぜない。性能の改善だけを理由に、原因の説明が正しいと結論しない。

### 6 今後の展望（やや丁寧）

**ラベル、枠、箇条書きは使わず、3つの段落で、この順に書く。** 事実・予想・知りたいことの区別は、段落と文末で示す。

1. 今回の結果から**確かに言えること**。文末は「〜であった」「〜が示された」。
2. まだ確かめていないが**今考えていること**。文末は「〜と考えられる」「〜の可能性がある」。
3. **次に知りたいこと**を1つ。文末は「〜を知りたい」。

この内容が、次の報告の「目的」に対応する。

## ルール 4. 探索型：章ごとの書き方

探索型は「何をどう動かして、何が見えたか」を短く伝える報告にする。読み手がすでに知っていること
（シミュレータの基本の作り、前の報告で説明した用語）は、繰り返さない。

### 1 目的（簡潔）

**何を知りたいかを、1〜2文で書く。**（例：「既存のルールベース入札手法が、このシミュレータでどう動くかを知る。」）
今の状況、仮説を立てられない理由、確認項目の一覧は、ここに書かない（REPのmdに書く）。
仮説を暗に含めて書かない。結果を見てからの説明は、最後の問いに書く。

### 2 実験

**3 つの小節は、どれも表でまとめる。** 本文は、表の前に 1〜3 文だけ書く（表が何を示すか、表に入らない定義）。
箇条書きや長い文章で条件・手法・特徴量を並べない（読みづらい）。表のセルは短く書く（1 セルは 1〜2 行。文章を詰め込まない）。

- **2.1 対象のアルゴリズム（丁寧）**：実験の条件の前に、**動かす手法がどんなものか**を表にする。
  列は「手法／見るもの（入力）／決め方」。1 手法 1 行で、既定のパラメータの値を入れる。
  手法に共通すること（何を決めるのか、手法どうしで何が違うのか）は、表の前に 1〜2 文で書く。
  詳しさの目安は、`chat_with_claude/` の解説と同じ水準。式は最小限にする。
  アルゴリズムを動かさない探索（データの確認など）では、「対象」として、扱うものを同じ形の表にする。
- **2.2 実験環境（簡潔）**：固定した条件と、変えた条件を、表にする（行の見出しは「固定／比較／掃引」など）。
  1 つの条件の中身は、セルの中で改行して 1 行 1 項目にする（何を・どの範囲で・何回）。
  既定のまま使ったものは「既定の設定」と書けば足りる（PV数、広告主の数、ティック数などを並べ直さない）。
  評価に使う量の定義は、表の前に 1〜2 文で書く。
- **2.3 取った特徴量（簡潔）**：成績のほかに記録した量を、「種類／記録した量」の表にする（1 種類 1 行）。
  取る理由（仮定）は、REPのmdに書き、報告には載せない。

**判断指標の節は置かない。** ただし、達成とみなす条件は、これまでどおり**実験の前に**REPのmdに書いてコミットする
（結果を見てから動かさない）。報告では、結果の最後に「達成したか」を1文で書くだけにする。

### 3 結果（簡潔）

観測した事実だけを書く（仮説検証型の「4 結果」と同じ）。段落の頭に、内容を表す短い見出し（「動作」「規模感」「手法の比較」など）を
太字で置き、E1 のような番号だけの見出しは使わない。表は、数値を並べて比べるものに限り、行を絞る。
最後に、実験の前に決めた達成条件（REPのmd）を満たしたかを1文で書く。

### 「結果から生まれた問い」は、PDFに書かない

探索型の報告（PDF）は、「結果」で終わる。結果から生まれた問い（確かに言えること／今考えていること／次に知りたいこと）は、
**REPのmdの「結果から生まれた問い」にだけ記録する**（ユーザーの決定、2026-10-10。PDFに置くと、次の報告との繋がりが悪くなるため）。
サマリーにも、「ここから〜という問いが生まれた」とは書かない（サマリーは、目的・方法・結果の要約にする）。
次に知りたいことが仮説にできるなら、次の検証の「2.2」に引き継ぐ（これはmdのほうから引く）。

## ルール 5. 書き終えたあとの確認

- [ ] 1ページ（多くても2ページ）に収まっているか
- [ ] タイトル・知りたいこと・仮説・予測・結論が、同じ1つの問いに答えているか
- [ ] 観測した事実と、解釈・推測が、文で分かれているか（文末が「〜であった」と「〜と考えられる」で使い分けられているか）
- [ ] 判断指標（探索型はREPのmdの達成条件）が、実験の前に書かれたものか。支持されない結果が明記されているか
- [ ] 判断が3つのどれかで書かれているか。支持されなかった結果が隠されていないか
- [ ] 性能の改善だけで、原因の説明が正しいと結論していないか
- [ ] （検証型）今後の展望が、事実・予想・知りたいことの3段落で、ラベルなしで書かれているか
- [ ] （検証型）知りたいことが1つで、次の報告の目的に繋がるか。次の報告の目的が、前の展望を受けて書き出されているか
- [ ] （探索型）PDFに「結果から生まれた問い」を書いていないか（サマリーにも）。問いは、REPのmdに書いたか
- [ ] REPのIDが既存の最大値の次で、親の問いのIDが正しく書かれているか（`\reportid`、`\questionid`）
