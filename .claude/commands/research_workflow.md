# research_workflow

このリポジトリでの研究の進め方を理解し、それに従って作業するためのコマンド。
研究（探索・仮説検証・実験・進捗報告・次の論点の相談）に関わる作業の前に、必ずこの文書を読む。

AuctionNet を題材に、「問題→仮説→検証」の形を踏んで、新しい入札方法を提案する修士研究を進める。
ここで決めた置き場所・ID・手順に従う。

## 使い方

```
/research_workflow [やりたいこと]
```

例：
```
/research_workflow 次に何を検証するか相談したい
/research_workflow H001 の実験結果を整理して事実に登録する
/research_workflow 新しい論点を立てる
```

引数がなくても、研究に関わる作業なら、この文書を読んでから始める。

---

## 実行手順

`$ARGUMENTS` を、今回やりたいこととして処理する。

### Step 0: 現状の把握

1. `research/MASTER.md`、`research/flow.md`、関係する論点の `node.md` と `facts.md` を読み、研究の現在地（進行中の論点、状態、未解決の問い）を把握する。
   `research/` がまだなければ、「ルール 6. 現状とのずれ」のとおり未作成であることを伝える。
2. 今回の作業が、次のどれに当たるかを決める。当たらなければ、ユーザーに確認する。

### Step 1: 研究の1サイクルを進める

1. **論点を決める**。直前の報告の「今後の展望」と、未解決の問いから選ぶ。仮説を1文で書ければ H、書けなければ Q。
2. **node.md を書く**（親・根拠の事実・仮説・予測・判断指標）。**実験の前に**書き、できれば先にコミットする。
3. **実験を回す**（`exp/`）。複数に分けてよい。
4. **事実を facts.md に登録する**。解釈は書かない。
5. **判断する**。判断指標に照らして、node.md の status を更新する。
6. **報告する**。`/make_progress_report` で REP を作る。観測した事実はIDで引く。
7. **次の論点を立てる**。新しい論点の node.md の親に、今回の論点を入れる。flow.md と MASTER.md の現在地を更新する。

作業が途中からのとき（実験後の整理、報告だけ、など）は、該当する番号から始める。
報告を書くときは `/make_progress_report` を使う。

### Step 2: 守ること

- 手順のどの段階でも、「ルール 1. 基本の考え方」を守る。特に、事実・仮説・結論を混ぜない。判断指標を結果の後に動かさない。
- ID は、既存の最大値を調べてから振る。再利用しない。
- `github/` は原則変更しない。パラメータは `params.json` で流し込む。
- 確認できなかった点、決めきれない点は、作り話で埋めず、ユーザーに確認する。

# ルール

## ルール 1. 基本の考え方

- 知りたいのは「何％良くなったか」ではなく、**どの説明を検証し、何が分かり、何がまだ分からないか**。大きな成果ではなく、着実な進捗を積む。
- 次の3つを、常に分けて扱う。
  1. **観測した事実**：実験で見たこと。条件・数値・図で示せる。
  2. **事実から考えた仮説**：原因についての推測。まだ確かめていない。
  3. **検証から言える結論**：判断指標に照らした判断（支持された／支持されなかった／まだ判断できない）。
- 性能の改善と、改善した理由の検証は別物。理由を確かめるには、その理由を直接変える実験が要る。
- 仮説を支持する結果だけを探さない。支持されなかった結果も、条件つきの**事実**として残す。
- **1つの論点に、1つの仮説**。クリティカルに検証し、一度に大量のことをしない。
- 判断指標は、**実験の前**に決める。結果を見てから動かさない。
- 型は2つ。仮説を1文で書けるなら**仮説検証型**、書けなければ**探索型**（無理に仮説を作らない）。型は論点ごとに選び、行き来してよい。
- 研究の流れは1本道ではなく**木**になる。事実Aから仮説B・C・Dが立ったら、次に進むのはそのどれか。この構造を失わないように管理する。

## ルール 2. 管理する単位とID

IDはすべて**ASCIIのみ**、全体で通し番号、**一度振ったら再利用しない**。（外部ツールとの対応づけに使う）

| 単位 | ID | 何か |
|---|---|---|
| 主題 | `T001` | 研究のゴールを支える大きな枝。修論の章に対応づける |
| 問い（探索型の論点） | `Q001` | 仮説がない段階の論点。「何が起きるか」を確かめる |
| 仮説（仮説検証型の論点） | `H001` | 検証したい仮説1つ |
| 実験 | `EXP001` | 実際に回した1回の実験。パラメータと結果を持つ |
| 報告 | `REP001` | 教授に送る進捗PDF。1つの論点を1枚で扱う |
| 事実 | `F001` | 実験で観測した、解釈を含まない事実1つ |

- **論点＝Q または H**。論点が、研究の木の節になる。
- 実験の数と報告の数は一致しなくてよい。1つの仮説を検証するために、複数の細かい実験を回し、まとめて1本の報告（REP）にする。
- 報告にまとめなかった実験も残す。
- 型（探索／仮説検証）や状態はIDに入れず、属性として持つ。

## ルール 3. ディレクトリ戦略（論点単位のフラット）

```
research/
├── MASTER.md                    # 最上位の地図（ゴール・範囲・主題と修論の章の対応・現在地・判断の履歴）
├── flow.md                      # 論点の木。各 node.md から生成する（手で編集しない）
├── Q001_{短い題}/               # 探索・問い
│   ├── node.md                  # 型・親・根拠にした事実・状態・日付
│   ├── facts.md                 # この論点で得た事実（F001…）
│   ├── exp/EXP001_{題}/         # params.json / results/ / meta.json
│   └── rep/REP001_{題}/         # 進捗報告.tex / .pdf / fig/
└── H001_{短い題}/               # 仮説。親は node.md に書く
    ├── node.md                  # 仮説・予測・判断指標を実験前に書く
    ├── facts.md
    ├── exp/EXP002_{題}/ EXP003_{題}/ ...   # 複数の細かい実験
    └── rep/REP002_{題}/         # 複数の実験をまとめた1本の報告
```

- フォルダ名は先頭にID。木を組み替えても、**フォルダは動かさず、node.md の「親」だけを書き換える**。
- 親は複数でもよい（厳密な木ではなく、親を複数持てる形）。
- 他の論点の事実を使うときは、コピーせず **IDで参照**する（`F003` など）。
- 置かないもの：自作の再利用コードは `src/`、本家コードは `github/`、会議メモは `MTG/`。
- 大きな生データは `.gitignore`。要約CSVと `meta.json` は残す。
- 実験が複数の論点から使われる場合は、`research/exp/` に出す（今は想定しない。必要になったら決める）。

### node.md のひな形

```markdown
---
id: H001
type: 仮説            # 仮説 / 問い
title: （短い題）
date: 2026-10-06
parents: [Q001]       # 親の論点ID。複数可
based_on_facts: [F001, F002]   # 根拠にした事実のID
status: 未着手        # 未着手 / 検証中 / 支持 / 不支持 / 判断不能 / 保留
reports: []           # REPのID
---

## 仮説（仮説型のみ）
今回検証する仮説を、1文で。

## 仮説を作るために使った結果
既に結果を見て考えた仮説なら、そのことを明記し、使った結果を書く。

## 予測
何を変えると、何がどう変わるはずか。途中の量も含める。

## 判断指標（実験の前に決める）
支持された／されなかった／まだ判断できない が、どの結果に当たるか。
```

探索型（問い）の node.md は、「仮説」「予測」の代わりに、**確認したい現象**と**達成とみなす条件**を書く。

### facts.md のひな形

```markdown
## F001
- 事実：（解釈を含まない1文。「条件Aでは、〜であった」）
- 条件：（この事実が成り立つ条件。一般化しない）
- 数値・図：
- 出典：EXP001
- 確からしさ：1回のみ / シード違いで再現 / 複数条件で再現
- 状態：有効 / 条件付き / 覆った（覆ったときは理由を書き、事実は消さない）
```

支持されなかった仮説の結果も、条件つきの事実として登録する。

## ルール 4. 実験の回し方

- **`github/` は原則変更しない**。パラメータを変えたいときは、`params.json` に書いて流し込む。アルゴリズムの追加だけは `github/` に加えてよい。
- 各実験は `exp/EXP{番号}_{題}/` に、`params.json`（変える値だけ）、`results/`、`meta.json`（論点ID・実行コミット・乱数シード）を置く。
- `params.json` は、報告の「検証方法」の表（固定する条件・変える条件）と対応させる。
- 本家の環境設定は gin（`github/config/test.gin`）。json から gin の上書き指定へ変換する実行スクリプト（`src/` に置く予定）を入口にする。

## ルール 5. Notion との対応

- Notion でも管理するので、IDはASCIIの通し番号にしてある。リポジトリのIDと同じ値を使い、対応をずらさない。
- 論理の木と状態の見える化に使う想定。リポジトリの node.md が元になる。
- Notion 側の構成（データベースの分け方など）は未定。決まったらここに追記する。

## ルール 6. 現状とのずれ（未対応）

次はまだ新方針に追従していない。作業のときに順に直す。

- `/make_progress_report` の出力先が `MTG/{日付}/` のまま。新方針は `research/{論点ID}_{題}/rep/REP{番号}_{題}/`。
- `progress_report.sty` が、連番カウンタ（`reportno`）で番号を振る形のまま。新方針は `REP001` と論点ID（`H001`）を明示的に渡す形（`\reportid`、`\nodeid` など）。
- `research/` ディレクトリ、`MASTER.md`、`flow.md` の生成スクリプト、`src/` の実行スクリプトは未作成。
- 進捗報告の書き方のルールは `.claude/commands/make_progress_report.md` にある。この文書の内容と食い違うときは、論点と事実の扱いはこの文書を優先し、報告書の書き方は make_progress_report を優先する。
